# 28. AI drafting with citations

Spec `spec-ai-drafting-001` · compatibility: behavior-compatible · leakage review: passed

## Summary

AI drafting assistance for construction projects. A project-scoped question-answering assistant retrieves passages from the documents and records a person may read, refuses when retrieval is weak, and otherwise returns claims that each carry citations (document, revision, sheet, page, section, in-app link); answers can be kept as a note or turned into a draft request for information. Autonomous agents (built-in, personal custom, and four project-enabled drafting agents) run a bounded tool loop under the invoking person's rights, attach a confidence-and-sources envelope, and only ever produce drafts or proposals that a person reviews before anything is written. An external-AI-client endpoint exposes read tools and proposal tools over an open JSON-RPC-based tool protocol for AI clients, authenticated by personal tokens, scoped to the owner's permissions, rate limited and audited. A provider configuration layer supports hosted providers plus self-hosted runtimes with per-person keys, model overrides, timeouts, recovery and safe-address checks. Cost and abuse limits, prompt-injection hygiene, and a faceted record search with saved searches complete the unit. Estimating and bill-of-quantities features are out of scope here.

## Behaviour

- Asking a question first collects every passage the caller may read in the project. If there are none, the result status is no-documents with zero confidence and no answer. _(beh-001; observed)_
- Passages are ranked by lexical relevance to the question with title, section and sheet number counting more than body text; passages from superseded document revisions are down-weighted but not excluded. A small number of top passages (observed: about six) is retained. _(beh-002; observed)_
- Retrieval confidence is the share (weighted by informativeness) of the question's meaningful terms that appear in the best passage, with a small bonus when the next passages also cover a comparable share. A rare-word match alone cannot produce high confidence. The confidence and the threshold applied are both returned. _(beh-003; observed)_
- Below the refusal threshold (observed default about 0.6; destination chooses) the result is not-found with no answer text; a few closest passages (observed: up to three) are returned as 'nearest' for orientation and are explicitly not an answer. The model is never asked to answer from weak retrieval. _(beh-004; observed)_
- When first-pass confidence is below threshold and a model provider is available, the question is rewritten into a few short keyword queries (different languages and specification vocabulary). Each rewrite is scored independently and replaces the first pass only if it yields higher confidence. Rewrite failure is silently tolerated. _(beh-005; observed)_
- Above threshold with a provider available, the model is given the numbered passages and the caller's language and must return claims, each with passage numbers and a short verbatim quote, using only the passages. Result mode is 'generated' only if at least one claim survives verification. _(beh-006; observed)_
- Claim verification drops any claim that has no citation, cites a passage that was not retrieved, or whose content words (or, when a verbatim quote is supplied, the quote) are not sufficiently present in the cited passages; the quote is the grounding test for claims written in a different language than the documents. Dropped claims are never shown uncited. _(beh-007; observed)_
- Without a provider, with AI disabled in the request, on provider failure, or when no generated claim survives, the answer falls back to extractive mode: the best-matching sentence of each of the top passages (a small number) that are nearly as relevant as the best one, each quoted and cited. If even that yields nothing the result is not-found. _(beh-008; observed)_
- The final answer text is the claims joined, each followed by bracketed citation numbers; cited passages are renumbered 1..n in order of first use and returned as citations carrying kind, source id, document id, title, revision, page, sheet number, section, a snippet (a few hundred characters), an in-app deep link and a score. _(beh-009; observed)_
- Documents are cut into passages of moderate size (observed: roughly 140 words) with overlap, per page (page breaks mark page boundaries), split further at numbered heading lines; a heading carries across a page break so continuing text is cited to its clause. Drawing sheets are marked as drawing kind with sheet number, title and revision. Structured records (requests for information, submittals, letters, minutes, contract terms) are cut into passages too. _(beh-010; observed)_
- Saving an answer as a note or as a draft request for information re-checks every submitted citation against what the caller can currently read and drops the rest, runs a warning-level rule that flags an answer with no citation (still saved, flagged), stores the answer with confidence, locale and validation outcome, and for the request-for-information target also creates a request in draft status whose body holds question, answer and a reference list and whose metadata records the origin and citations. _(beh-011; observed)_
- The kept-answers list returns only the caller's own answers for the project, newest first, with the total count and paging. _(beh-012; observed)_
- The assistant screen requires an active project; asking needs a minimum question length of two characters and a bounded maximum; source-kind filters toggle; results show a confidence indicator (tone depends on distance above threshold), a note whether the text was AI-written or quoted, claims with citation markers and optional verbatim quote, source cards that open the source only for in-app links (links that are absolute or protocol-relative are never followed), and save actions only for answered results. _(beh-013; observed)_
- External tool endpoint (POST) accepts one message or a batch, answers success with a JSON body, answers 202 with no body when only notifications were sent, answers 405 for GET or DELETE (no server-initiated stream, no session identifier issued). _(beh-014; observed)_
- Initialisation negotiates the protocol version (the client's if supported among the supported versions, otherwise the newest), declares tool capability only with no list-changed notifications, returns server identity and version and short usage guidance telling clients where to begin, that money values are decimal strings, and that proposal tools change nothing until a person applies them and need an honest confidence and a rationale. Guidance wording is the destination's own. _(beh-015; observed)_
- Tool listing returns only tools the token's owner may currently use: a proposal tool requires a token issued with proposal ability, every tool requires its module to be enabled and the owner's role to hold the module read (or create) permission. Each tool definition includes a title, description, input schema and read-only/idempotent hints (read tools read-only; none destructive). _(beh-016; observed)_
- Read tools expose read-only views of the owner's projects: the project list and one project summary, schedule and risk-register views (the schedule view reports whether critical-path calculation has happened and never recalculates), latest validation reports, counts by status and oldest open items of requests for information, submittals and punch items with due dates and overdue flags (sections the owner's role cannot read are omitted), and document metadata only, never contents (folder permissions applied). Each tool has a bounded result limit with a default. Money values, where present, are decimal strings. Estimating and cost-catalogue tools are optional and out of scope. _(beh-017; observed)_
- Proposal tools mirror the in-app assistant's propose-style actions whose modules are enabled. Each requires a confidence and a one-line rationale; a call stores a proposal marked as originating from an external client and returns the proposal id, status, title, project, confidence and fields. Nothing is changed in records; a person reviews and applies proposals in an in-app review view under the record's own permissions. _(beh-018; observed)_
- Tool results carry a text block (summary line then JSON), the same data as structured content, and an error flag. Text beyond a generous size cap is truncated with a trailing note telling the client to narrow the request. _(beh-019; observed)_
- Per-person tool-server settings default to disabled when no record exists; the per-minute budget has a default and a bounded range (observed: default 60, range 1 to 600). Settings can be read and changed by anyone holding the viewer-tier 'use' permission; a change is audited with before and after values. _(beh-020; observed)_
- Token creation issues a personal access token with a recognisable fixed prefix, a name (bounded length), an expiry in days within a bounded range (observed: default 90, up to a year) and an optional proposal ability (default on); the secret appears only in the creation response. Listing never shows secrets. Revoking deactivates the token; another person's token or a token not issued for the tool server answers not-found. Creation and revocation are audited. _(beh-021; observed)_
- A recent-calls feed (bounded page size, newest first, with total) shows tool, kind, outcome (ok, error, denied, rate-limited), duration, project, token prefix, proposal id and error code. A setup validation report summarises findings: rate limit out of range (error), active token without expiry (warning), active token unused for a long period or never used a month after creation (warning), too many active tokens (warning), repeated refused calls in a day (warning), enabled with no active token (info). Thresholds are observed values (about 90 days, 30 days, more than five tokens, ten refused calls); the destination chooses its own. _(beh-022; observed)_
- Settings card: a switch; a rate input that shows a range error and offers Save only when changed and valid; token creation disabled until the switch is on and a name is entered; after creation the secret and a ready client configuration (a server entry with HTTP transport, the endpoint URL built from the page origin, and a bearer authorisation header) plus connection-check instructions are shown once; revoke asks for confirmation first; a pending-proposals count with a review action that opens the assistant's review view; validation findings (or a no-problems line); a recent calls table. _(beh-023; observed)_
- Provider resolution: the person's preferred model name selects a provider by keyword, with the more specific self-hosted runtime preferred over a more generic provider match; if that provider's stored key is missing or cannot be decrypted, any other stored key is tried in a fixed priority order; then a saved self-hosted endpoint; then operator-level fallback configuration, preferring the chosen provider. Keyless self-hosted runtimes are valid with no key. _(beh-024; observed)_
- Model choice: per-provider defaults exist; a person may override the model id per provider (blank clears); free-text model ids pass through unchanged. If a provider rejects the model (unknown, deprecated, retired), the call automatically retries with provider-stable fallback models before failing with an actionable message naming the rejected model and where to change it. _(beh-025; observed)_
- Timeouts: effective wait is an explicit caller value, else the person's saved per-provider value (bounded range), else a server setting, else a built-in default of a few minutes. A person-chosen timeout also lifts the shorter per-step cap that agents apply by default. _(beh-026; observed)_
- Self-hosted runtimes (two kinds, one doubling as a generic compatible endpoint): the person may save a host root; the full chat path is completed automatically; an optional bearer key may be saved (stored encrypted, an empty value clears it) or taken from a server-level fallback; a per-endpoint tool mode of auto, on or off exists (auto tries tools and remembers a refusal for a limited time per endpoint and model, then sends plain requests). Addresses are re-validated at call time; endpoints are scoped to the calling person and one person's endpoint is never used for another person. _(beh-027; observed)_
- Provider error mapping gives actionable messages without leaking secrets: invalid or expired key, model rejected, access to model denied, rate limit hit, image unusable, empty or filtered provider reply (including replies that carry content in alternative shapes or only a reasoning trace), and a generic provider error with a truncated detail. A paid reply is never silently discarded. _(beh-028; observed)_
- Structured replies are extracted from model text by trying a direct parse, then a fenced block, then the outermost brackets or braces; failure yields nothing rather than an error. _(beh-029; observed)_
- Settings read returns only whether each key is set (never the key), the saved self-hosted endpoints, tool modes and defaults, timeouts and default timeout, per-provider model overrides and defaults, preferred model, and a readiness flag true when a usable cloud key exists or a self-hosted endpoint is configured. Settings update changes only supplied fields, encrypts keys at rest, and publishes an update notification. _(beh-030; observed)_
- The connection test requires the settings-update permission, accepts any known provider, answers success with latency and model or a failure message (missing key, undecryptable key, provider error, generic connection failure with detail only in server logs), uses the same model and endpoint as real calls, and limits its wait to a short deadline. _(beh-031; observed)_
- Agent runs: a start request returns at once with a running record; the loop continues in the background and the client polls the run (with steps). Optional project link is access-checked. A repeated start with the same idempotency key from the same person within a short window (observed: ten minutes) returns the original run instead of starting another. Run listing is the caller's own (bounded page size), run reading answers not-found for another person's run. _(beh-038; observed)_
- The run loop alternates model steps and tool steps until a final answer, with distinct failure reasons for: no provider, iteration limit, token budget (checked after each step), total wall-clock budget (checked before each step), per-model-call timeout, model error, and a malformed model step. A tool failure is not fatal: the error is fed back to the model. Tool output is truncated to a bounded size before re-entering the model. Limit values are chosen by the destination (observed order of magnitude: single-digit iterations, tens of thousands of tokens, about two minutes in total, under a minute per call). _(beh-039; observed)_
- Analytical built-in agents (a defined set covering analysis, reporting, compliance, anomaly review and similar read-and-assess tasks) are told to end their answer with a structured trust block; the block is parsed off and stored separately. Mechanical drafting and classifying agents are excluded so any JSON they output is never stripped. _(beh-040; observed)_
- Trust envelope: confidence in 0..1 (a value 1 to 100 is read as a percentage, larger or negative values clamp, non-numeric or boolean become absent), a short rationale, sources (kind, real reference, optional label and finite score; malformed entries dropped), and what would raise confidence. Parsing never fails: with no or malformed block the original text is kept and the envelope is empty. An empty envelope is stored as none. _(beh-041; observed)_
- Accuracy loop: a person may record whether a run's answer was correct (with optional note), only for their own runs (otherwise not-found); the scoreboard per agent reports count, Brier score, mean confidence, observed correct rate, expected calibration error and ten confidence bins. A generic correct/incorrect verdict endpoint records feedback for any AI surface (project access-checked when a project is supplied) and a roll-up reports totals and per-surface correct rate, absent rather than zero when there are no verdicts. _(beh-042; observed)_
- Trust card (frontend): shows confidence percent, rationale, cited sources and the improvement hint for completed runs that have an envelope, offers correct and incorrect verdict actions, after a verdict shows the recorded state and note with a change action, and renders nothing for runs without an envelope or still running. _(beh-043; observed)_
- Custom agents belong to one person: create, read, replace, delete (others' agents answer not-found); creating or running needs editor-tier permission. Display fields: name, tagline, description, category (unknown folds to general), icon, example prompts. Instructions come from a guided form (role, goal required, audience, output format, extra guidance) that is compiled into instructions ending with a standing guardrail to state assumptions, not invent project facts and expect human review, or from raw instructions; neither present is rejected. _(beh-045; observed)_
- Tool grants for a custom agent are limited to existing tools the owner already has permission for (each tool maps to a module permission; an unmapped tool needs only the run permission); selecting one the owner lacks is refused with the tool and missing permission identified; unknown tools are dropped; with no tools the agent is prompt-only with a small iteration cap, with tools it receives the standard iteration budget. The tool picker disables tools whose required permission outranks the person's role, resolving unknown or absent roles to no authority and role aliases to the canonical tier they map to. _(beh-046; observed)_
- Schedules: a five-field cron expression (UTC) is validated (malformed refused), the next run time is computed when enabled, a paused schedule keeps its cron with no pending run, a schedule input text is stored (a generic default is used when blank), and deleting a schedule keeps tool grants. A once-a-minute poll fires due agents one at a time under the owner's identity, advances the next-run time before running so a crash cannot loop, disables a schedule whose cron cannot be parsed, and never stops the tick for one failing agent. _(beh-047; observed)_
- Event triggers: a catalogue lists triggering events (for example a request for information created, a document uploaded); events not yet available are flagged. A subscribed custom agent runs when its event fires, with a short factual prompt carrying record identifiers, tagged by trigger source; unknown trigger names are dropped on save. _(beh-048; observed)_
- A failed automated (scheduled or event-fired) run notifies its owner in-app with agent, reason and trigger; manual failures are shown inline only. Automated runs have their own listing, and a project insights view distils the caller's recent completed runs with output into cards (title, summary, confidence, severity defaulting to info). _(beh-049; observed)_
- Project agent catalogue: each project sees four agents with enabled state, configuration (defaults merged with project overrides) and a per-run token limit (default and range chosen by the destination). A run requires: project not halted, agent enabled on the project, required inputs present. A run creates an audited run record with tool-call and observation steps and a pending draft carrying payload, confidence and sources; nothing else is written. _(beh-052; observed)_
- Draft content is produced by deterministic logic from read-only tool results; a model, when available and use is not disabled, only adds a short narrative (a few sentences, facts only, references kept exactly) within the project's token limit. A missing provider or narrative failure leaves the draft intact with a recorded skip reason. _(beh-053; observed)_
- Request-for-information drafter: subject is the first sentence of the question (length-capped, with a neutral fallback); references (a small number of sheets/specification sections) are included only when retrieval confidence reaches the assistant's threshold, otherwise the draft keeps only the question with confidence capped at a low value (observed: 0.3). An attached markup's label is searched together with the question. Referenced sheets and specification sections are listed. _(beh-054; observed)_
- Daily report drafter: for a given calendar date it gathers timesheets, diary photos, voice notes, weather and deliveries of the project and composes labour (distinct workers, total hours), weather, deliveries, notes, photos, inputs present and missing, sources per line, and a confidence equal to the share of the five expected inputs present. An invalid date is refused; an unavailable source does not blank the others. _(beh-055; observed)_
- Clause reviewer: checks contract passages against a configurable checklist (default covers common commercial terms such as payment terms, liquidated damages, indemnity, retention and termination, with multilingual patterns and configurable limits for payment period and retention percentage). Each item is ok, flagged (with reasons such as risky wording, no cap, payment period or retention over limit, no release) or missing when no passage matches; risk is high for risky wording or uncapped damages, medium for other reasons, low otherwise; findings cite a few passages; confidence is the share of checklist items found. _(beh-056; observed)_
- Submittal checker: finds requirement sentences in the submittal's specification section (a bounded number), marks each addressed when at least about half its content words appear in the submittal's own text and unclear otherwise, never marks failure; recommendation is ready for review, request missing information, or section not found (confidence zero); confidence scales retrieval confidence by the addressed share. _(beh-057; observed)_
- Draft review: accept or reject only pending drafts (a second decision conflicts), with optional note and optional edits merged into the draft and flagged as edited by a reviewer; accepting a request-for-information draft with apply creates a request in draft status carrying question and references and a back-link to the draft. Listing is paged with a bounded size; run history lists catalogue runs; a rule reports info-level findings for pending drafts older than the agent's review window (per-agent window; shorter for the daily reporter). _(beh-058; observed)_
- A workflow-automation step can run a catalogue agent for a project (daily reporter defaults to today), obeying the same halt, enablement and token limit, running with the lowest role, and reporting success with run id, draft id, confidence and summary, or a failure code. _(beh-059; observed)_
- Document-analyst agent: its single tool searches the project's indexed document text (a few hits with document id, name, snippet, score), distinguishes 'index unavailable or empty or no access' from 'indexed but nothing matched' (the latter instructs to answer that nothing was found), and the agent is instructed to answer only from tool results, cite documents and never fabricate. _(beh-060; observed)_
- Record search (any project member): filters are free text (terms of two or more characters), party (case-insensitive), record type, entity reference (intersection) and an inclusive ISO date window; filters combine with AND; with no filter every record is listed ranked by base relevance and recency. Score blends base relevance, share of text terms matched anywhere in title/body/references, share of entity references matched, a party bonus and a recency bonus decaying over about a year relative to an optional reference date; results are ordered by score, then newest date (unknown last), then id, deterministically. _(beh-061; observed)_
- Each result returns type, id, title, snippet (a few hundred characters), owning module, party, event date, entity references, score, matched facets and a reference to the matched record (module, type, id, date). Only documents, correspondence and change orders are searched, newest first and bounded per source. _(beh-062; observed)_
- Saved searches are private to their owner and project. Saving with the same facets as an existing pin renames and revalidates it instead of duplicating; at a bounded pin count (observed: thirty) the least-used pin is evicted rather than refusing; update can rename and/or re-point; replay records a use count and last-used time so pins rise in the list; delete removes. Facets are trimmed, unknown keys dropped. Foreign or missing pins answer not-found. _(beh-063; observed)_
- Saved-search validation: a label is required (blank is replaced by a description of the facets), at least one facet must be set, dates must be ISO calendar dates and a two-sided window must not run backwards (all three block with a validation-failure response and findings); an unindexed record type is a warning only. Result is persisted as passed, warnings or pending (when validation could not run or resolved to no rules). _(beh-064; observed)_
- Record search screen: needs a project (a prompt to choose one is shown otherwise); search runs only on explicit commit; client-side sort by relevance, newest, or type, paging with a small page size, term highlighting, deep links by type (documents open the file manager on that file; correspondence and change orders open their lists; unknown types render as plain text), recent searches kept on the device, pinned searches kept on the server, a save action only for meaningful queries, replaying a pin runs it and records use quietly (failure of that write is not shown). _(beh-065; observed)_
- Long AI calls are allowed to run past the ordinary request deadline (observed: ordinary 90 seconds, long calls up to five minutes) with a single attempt and no replay; a caller's cancellation aborts immediately and is not queued for offline replay; ordinary reads and writes keep the ordinary budget; timers are released after completion; a server refusal message is surfaced and not retried; file uploads keep multipart form encoding with authentication and no forced content type. _(beh-066; observed)_
- Recent assistant history is stored locally under a per-person key (anonymous when no identity), newest first, capped by a maximum entry count with oldest evicted, a re-added id moves to the front, versioned storage that is discarded when the version or shape differs, malformed entries dropped while valid ones kept, and clear empties both memory and storage. _(beh-067; observed)_

## Inputs

- Ask request: project id, question (minimum two characters, bounded maximum), locale (short code, default English), optional list of source kinds from a closed set (unknown kinds are refused with a validation failure), and an AI-use flag (default on). _(in-001; observed)_
- Save-answer request: project, question, answer (bounded), claims, citations, confidence 0..1, locale, target note or draft request for information, optional request subject (bounded, falling back to the question, truncated). _(in-002; observed)_
- External endpoint credential: sent either as an API-key style header or as a bearer authorisation value that carries the fixed token prefix (so it cannot be confused with a session credential); the protocol version header, when present, must be a supported version; body must be JSON, bounded in size. _(in-003; observed)_
- Tool call parameters: a non-empty tool name and an optional object of arguments (null treated as empty). Identifier arguments must be well-formed UUIDs; integer arguments are clamped into the tool's bounds and non-integers are refused; text arguments must be strings, trimmed and truncated to a maximum length. Proposal tools additionally require confidence and rationale. _(in-004; observed)_
- Agent run start: agent name (built-in or custom slug), user input, optional project, optional idempotency header. Custom agent create/replace: display name, tagline, description, category, icon, example prompts, guided spec or raw instructions. Schedule: cron expression, enabled flag, schedule input, triggers. Tools: list of tool names. Outcome: correct flag and optional note. Feedback: surface, correct flag, optional project, reference, note. _(in-005; observed)_
- Catalogue inputs: the request-for-information drafter needs a question (markup and photo optional); the daily reporter needs a date; the clause reviewer takes an optional document or contract; the submittal checker needs a submittal. Configure: enabled flag, configuration object, token limit within a bounded range. Halt: flag and a bounded reason. Review: accepted or rejected, bounded note, apply flag, edits. _(in-006; observed)_
- Provider settings update: any provider key (trimmed), self-hosted host roots, optional endpoint key, tool mode per self-hosted endpoint (auto, on, off; blank resets), timeouts per provider (bounded range, null clears), preferred model (bounded length), model overrides per provider. Unknown extra fields are tolerated for existing callers. _(in-007; observed)_
- Record search input: project id (required) and optional text, party, record type, entity, date-from, date-to and an optional reference date. Saved-search facets and label are length-bounded. _(in-008; observed)_

## Outputs

- Ask response: status (answered, not-found, no-documents), mode (generated, extractive, none), question, locale, answer text, confidence, threshold, claims (text, citation numbers, optional quote, quoted flag), citations, nearest passages, number of passages searched, tokens used (model rewrite plus answer calls). _(out-001; observed)_
- Saved answer record: id, project, question, answer, claims, kept citations, confidence, locale, target kind, target id (request id when created), validation (status passed or warnings with findings), created time. Saving returns a created response. _(out-002; observed)_
- Tool protocol responses use the standard JSON-RPC envelope: success with result, or error with a numeric code and message (standard codes for parse, invalid request, unknown method, invalid params, internal error, plus one implementation-defined code for rate limiting carrying the limit and a retry hint). A tool-level failure is a successful call whose result has the error flag and a code and message. _(out-003; observed)_
- Run response: id, agent, project, owner, status, trigger source (manual, schedule, event, catalogue), failure reason, input, final output, trust envelope, iterations, tokens, times, ordered steps (thought, tool call, observation, answer, error). Catalogue endpoints return catalogue with halt state and reason, run result with run and draft, draft pages, run pages. _(out-006; observed)_
- Tool-server settings response includes enabled, rate limit, the endpoint path and supported protocol versions; token responses include id, name, prefix, active flag, proposal ability, expiry, last use and creation time and, only on creation, the secret. _(out-007; observed)_
- Record search response: count and ranked results; saved-search response: id, project, label, facets, signature, use count, last-used time, timestamps, validation status and findings (rule, severity, message, suggestion). _(out-008; observed)_

## States and transitions

- Agent run: running, then completed or failed with a failure reason; the run record is created before the background work begins; automated runs that fail also create a notification. _(st-002; observed)_
- Agent draft: pending, then accepted or rejected exactly once; accepted with apply for a request-for-information draft also records the created request id. A second review attempt is a conflict. _(st-003; observed)_
- Token: active until revoked or expired; revocation is immediate and permanent. Per-person external access: off (default) to on and back, taking effect on the next call; a valid token whose owner has switched access off is refused with its own error code. _(st-004; observed)_
- Project halt switch: when on, every catalogue run on the project is refused with a locked response and the stored reason; turning it off allows runs again. _(st-005; observed)_
- Run outcome verdict: unset, then correct or incorrect; a person may change it later (the recorded outcome, time, person and note are kept on the trust data). _(st-006; observed)_
- Schedule: set (next run computed) to fired (next run advanced before the run) to paused or deleted; a bad cron on firing moves the schedule to disabled with no next run. _(st-007; observed)_

## Timing and ordering

- Ask pipeline order: collect readable passages, rank, optionally rewrite and re-rank when weak, apply the refusal gate, optionally generate and verify claims, fall back to extractive, build the numbered answer. _(ord-001; observed)_
- Tool endpoint order: origin check, version header check, credential resolution (auth transaction ended before work), body size check, parse, then dispatch under the owner's tenant and cost scope. Tool call order: validate request, rate limit, authorise (scope, module, permission), run in a nested transaction, audit. Denied and rate-limited calls are audited too. _(ord-002; observed)_
- Rate limiting is a sliding one-minute window per token; a changed limit gives a new budget on the next call. _(ord-003; observed)_
- Agent run guard order: wall-clock check before each model call, token budget check after accumulating that step's tokens, model reply handled (final, tool call, or malformed), tool run with context re-injection, observation truncated and fed back. _(ord-004; observed)_
- Catalogue run guard order: halted, disabled, missing inputs; then gather via read-only tools, deterministic draft, optional narrative, persist draft, finish run with trust data of confidence and sources. _(ord-005; observed)_
- Scheduler ticks once a minute and runs due agents sequentially; event-fired agents also run sequentially to bound model concurrency. _(ord-006; observed)_
- Search results are ordered by score descending, then event date newest first with unknown dates last, then record id ascending; saved-search lists order most useful (used most and most recently) first. _(ord-007; observed)_

## Edge cases

- Retrieval reads are bounded (documents, records per record family and passages per question each have a ceiling). A failure to read one source family never hides the others. _(edge-001; observed)_
- A question made only of uninformative words yields no hits and therefore not-found with zero confidence; only the first few query rewrites are used; a rewrite in another language has near-zero coverage until translated, which is why each is scored on its own. _(edge-002; derived)_
- A saved answer with no surviving citation is still saved but its validation status is warnings; citations the caller can no longer read are silently dropped at save time. _(edge-003; observed)_
- Validation engine failure at save time does not block saving the answer. _(edge-004; observed)_
- A JSON-RPC message with a boolean or null id, a non-string method, a missing method, or non-object params is rejected with invalid-request or invalid-params; a response message from the client is accepted and ignored; an empty batch is invalid; a batch yields only the non-empty answers (none means 202); a notification never gets an answer even for an unknown method. _(edge-006; observed)_
- A rate-limited single request returns HTTP 429; a rate-limited call inside a batch returns the error in the batch with an overall 200. _(edge-007; observed)_
- With no schedule in a project the schedule tool returns an empty result with a plain statement; a schedule id not in the project is a tool error. _(edge-008; observed)_
- Agent tool calls to an unknown or non-allowed tool produce an observation listing available tools rather than failing the run; observations over the cap are replaced by a truncation marker with original size and a preview. _(edge-009; observed)_
- Explicit text protocol for tool calls: a model reply containing one structured tool-call block is a tool call (prose before it becomes a thought); anything else, including malformed blocks, is the final answer. _(edge-010; observed)_
- Provider with tools refused: the request is retried once without the tool schema and with the plain instructions; the refusal is remembered only in automatic self-hosted mode. _(edge-011; observed)_
- A stored key that no longer decrypts (server encryption key changed) is reported as such, never sent as an anonymous request; another working key or fallback key is tried first, and only if none works does the error say to re-enter the key. _(edge-012; observed)_
- Replaying an agent start with an idempotency key whose cached run belongs to a different person is ignored. The cache expires entries after a short window and is size-bounded with oldest evicted first. _(edge-013; observed)_
- Event triggers need a resolvable project; without one nothing fires. Subscribers fire only when their creator owns or belongs to the event's project. _(edge-015; observed)_
- Saved search with no facets, or a reversed or malformed date window, is refused; an unindexed record type is accepted with a warning because indexed types are expected to grow. _(edge-016; observed)_
- Stored local history that is corrupt, of another version, or of the wrong shape loads as empty without error and later appends still work. _(edge-017; observed)_

## Errors

- Tool endpoint auth failures are ordered: no credential gives 401 with a missing-token code; unknown, revoked or expired credential gives 401; a valid key not issued for external-client use gives 403; an inactive or missing owner gives 401; owner switched access off gives 403 with a distinct code. 401 responses include an authenticate challenge. Each carries a machine-readable code and a human message (destination chooses codes). _(err-001; observed)_
- Other endpoint errors: foreign browser origin gives 403 (clients without an origin pass; configured and same-host origins pass); unsupported protocol version header gives 400 listing supported versions; oversized body gives 413; invalid JSON gives 400 with a parse error. _(err-002; observed)_
- Tool call failures: missing name or non-object arguments is invalid-params; unknown tool is invalid-params; over budget is the rate-limit error and audited as rate-limited; not allowed returns a tool error with a distinct stable code for each of: token lacks proposal ability, module disabled, permission denied; project missing or inaccessible returns an identical project-not-found tool error; invalid identifier or integer arguments give an invalid-arguments tool error; unexpected failure gives a generic tool-failed error and the details stay in server logs. _(err-003; observed)_
- Document assistant HTTP errors: invalid caller identity 401; inaccessible project (not-found posture); unknown source kind 422; missing permission 403; list limit outside the allowed range rejected. _(err-004; observed)_
- Provider-related failures during AI calls give a client error with the mapped sanitised message and a settings hint where relevant; other failures give a gateway-style error with a generic message. _(err-005; observed)_
- Provider settings validation: self-hosted address in a blocked range (link-local or cloud metadata) or outside a configured allow list is refused with a validation failure at save time and again at call time after address resolution; loopback and private addresses are allowed; a tool mode for a non-self-hosted provider or an unknown mode is refused; a timeout outside the range or for an unknown provider is refused; connection test with an unknown provider gives a client error. _(err-006; observed)_
- Agent errors: unknown agent on start 404; run or custom agent not owned or missing 404; custom agent with neither guided goal nor instructions 422; malformed cron 422; tool grant beyond the owner's permission 403 naming tool and permission; apply with no proposals 422; missing permissions 403. _(err-007; observed)_
- Catalogue error conditions map to statuses: unknown agent or draft not found 404, project halted 423, agent not enabled 409, draft already reviewed 409, missing required input 422, invalid decision 422, invalid date 422. _(err-008; observed)_
- Saved-search blocking validation failures give 422 with a message and every blocking finding; foreign or missing saved search 404. _(err-009; observed)_
- Frontend surfaces: ask failure, save failure, token create or revoke failure, settings save failure each show an error notice; a search failure shows a failure empty state with the message; failing to copy shows a hint to copy by hand. _(err-010; observed)_

## What it must not do

- The assistant never answers from weak retrieval, never shows an uncited or ungrounded claim, and never uses nearest passages as an answer. _(neg-001; observed)_
- External clients never change records: no tool writes except to store a proposal; document tools never return file contents; a tool-server token cannot reach ordinary programmatic routes and a general-purpose key cannot reach the tool endpoint. _(neg-002; observed)_
- Agent output is never auto-applied: scheduled, event-fired, catalogue, custom and workflow-step runs only produce text, proposals or pending drafts; applying or accepting is a separate human action with its own permissions. _(neg-003; observed)_
- Provider keys are never returned by any endpoint, never echoed in errors, and one person's self-hosted endpoint or timeout never influences another person's calls. _(neg-004; observed)_
- Argument values of external tool calls are never written to the audit log; only a bounded list of argument names is. _(neg-005; observed)_

## Security

- Data scoping before ranking: a passage the caller may not read never enters retrieval, so it cannot surface in an answer, snippet, nearest list or confidence. Each source family is gated on its own read permission; documents with a restricted classification are readable only by manager-tier roles, admin and the uploader; the caller must own or belong to the project. _(sec-001; observed)_
- Citations are re-validated at save time against current readability, so permission loss between ask and save cannot leak text into a saved record. _(sec-002; observed)_
- Existence-oracle defence: missing and foreign resources answer identically (not-found) for agent runs, custom agents, saved searches, tokens, projects reached through tools, and proposals targeting a foreign project; project-linked inputs always pass a project access check. _(sec-003; observed)_
- Token security: tokens are stored hashed, shown once, expire, can be revoked, track last use, require an explicit access scope, and are checked for owner activity and the owner's own on/off switch on every call. Proposal ability is a separate scope. A token never reaches further than its owner's current role. _(sec-004; observed)_
- Browser-origin protection (anti DNS-rebinding): requests carrying a foreign origin are refused; requests without an origin pass; stateless, no push channel. _(sec-005; observed)_
- Prompt-injection hygiene: free-form text going into prompts has control and invisible-control characters removed (all but ordinary whitespace) and is length-capped; user content and document text are placed in a clearly delimited untrusted-content region with an instruction to treat it as data and ignore embedded role changes; forged closing markers in the input are neutralised so content cannot escape the region; text visible in images is treated as annotation, not instructions; question-answering and agents are told to use only supplied passages or tool results. _(sec-006; observed)_
- Agent identity cannot be forged: the invoking person and project are injected by the runner as trusted context; any context a model supplies in a tool call is stripped; data-reading tools re-verify project membership each call and fail closed (treated as no access, with the same shape as an empty index) on any lookup error. _(sec-007; observed)_
- Agents never widen their owner's reach: tool grants require the owner's current role to hold the tool's permission; apply needs run plus create permissions; scheduled runs execute as the agent owner; event triggers fire only for creators with access to the event's project, preventing cross-tenant firing and payload leakage; catalogue tools are read-only and scoped to the trusted project. _(sec-008; observed)_
- Self-hosted endpoint safety: user-supplied addresses cannot target link-local or cloud-metadata ranges nor fall outside an operator allow list; validated at save and again at dispatch after name resolution; the connection test has a short deadline to limit the blast radius; only self-hosted providers accept a user address, so a person cannot redirect their key to an arbitrary vendor host. _(sec-009; observed)_
- Cost and abuse limits: AI-using endpoints pass a per-person request budget (configurable) and return the remaining count in a response header; external clients have a per-token per-minute budget; agent runs have iteration, token, wall-clock and observation caps; catalogue runs have a per-project token cap; scheduling is sequential; idempotency keys stop duplicate paid runs; tool output text is capped. _(sec-011; observed)_
- Permission tiers: asking the assistant and reading settings or runs are viewer-tier; saving answers, running agents, creating custom agents, applying proposals, provider settings changes and the connection test are editor-tier; configuring catalogue agents and the project halt are manager-tier; accepting or rejecting drafts is editor-tier; enabling external access and managing one's own tokens is viewer-tier while proposal ability for tokens is editor-tier; record search itself needs project access only. _(sec-012; observed)_
- Auditability: every external tool call (including denied and rate-limited) writes an audit row with tool, kind, outcome, duration, token prefix, project, proposal id, error code and argument names; settings changes, token creation and revocation are audited; every agent step is persisted; token usage is stored per run. _(sec-013; observed)_
- Sensitive-data handling: documents with a restricted classification are excluded for lower roles in assistant, agents and external tools (folder-level permissions in the document tool); external tools return metadata only for documents; no explicit personal-data redaction step for model input is specified (see open questions). _(sec-014; observed)_

## Invariants

- Every claim shown as an answer cites at least one retrieved passage and is grounded in it; confidence is always reported alongside the threshold. _(inv-001; observed)_
- Ranking and confidence are deterministic for the same passages and question; the record search ordering is total and stable; the faceted search is a pure function of records, query and reference date. _(inv-002; observed)_
- A model never decides a flag, status or risk level in the project drafting agents: those come from deterministic rules over cited passages; the model only adds optional narrative. _(inv-003; observed)_
- Confidence values stored or shown are always within 0..1 or absent; percentages are normalised; a missing confidence is never replaced by a placeholder. _(inv-004; observed)_
- Human confirmation: nothing the AI drafts becomes a project record without an explicit person action; AI-originated records are tagged with their origin (answer, agent, run or external client) for traceability. _(inv-005; observed)_
- Per-person isolation: settings, runs, custom agents, kept answers, saved searches, tokens and endpoints are visible and usable only by their owner (project-shared surfaces apply project access). _(inv-006; observed)_

## Notes

- The tool endpoint speaks an open JSON-RPC 2.0 based tool protocol for AI clients (handshake, liveness check, tool listing, tool invocation; stateless; single JSON replies; several dated protocol versions supported, newest preferred). Interoperability with off-the-shelf AI clients requires standard envelope shapes, standard error codes and a bearer-style credential; routes, token prefix, tool names and server name are not required to match any origin value. _(cmp-001; derived)_
- Numeric limits in this spec (confidence threshold, budgets, caps, windows, retention, pin counts, deadlines) are observed ordinary behavioral parameters given so behavior can be matched in spirit; the destination chooses its own values, should keep their ordering, and should keep each limit explicit and user-visible where noted. _(cmp-002; derived)_
- The destination already has its own sign-in, shell, documents and request-for-information features. Adapter points this unit relies on: a project access check, a role-to-permission table with viewer, editor and manager tiers, an event bus, a validation rule engine, an audit log, in-app notifications, a request-for-information creation path, a document index with page-separated text and sheet register, and per-user secrets storage. These may need adapting rather than copying. _(cmp-003; inferred)_
- User-facing wording is localised with default-language fallbacks; the destination localises its own copy and does not reuse origin strings. _(cmp-005; inferred)_

## Non-goals

- No implementation code is generated.
- Reproducing the origin's private structure, identifiers, prompts, strings or file layout.
- Specific model names, provider endpoints, vendor lists or default model ids.
- Estimating, bill-of-quantities, cost-catalogue, cost-advisor, element matching, photo categorisation, plan reading and conversational intake features.
- Demo-mode sample data seeding.
- Backward-compatibility with legacy clients of the origin system.
- Do not reproduce origin provenance markers.

## Open questions (decisions for QC Manager)

- Which per-person AI request budget and window should the destination use, and where is it enforced?
- The set of proposable actions offered by the destination's in-app assistant, its review view and the apply path are outside this unit; the destination must define them.
- Whether destination document text is indexed page-by-page with a sheet register (needed for page-level citations) must be checked against the destination.

- How should an unregistered permission be treated during retrieval gating: fail open to the lowest tier, or fail closed?
- Should idempotency keys and rate-limit windows be shared across processes or instances, or is per-process state acceptable?

- Backend automated-test expectations for error codes were not available; error-code expectations are derived from observed behavior and need destination confirmation.
- Which of the optional analytical built-in agents does the destination want, given that estimating-related agents are out of scope?
