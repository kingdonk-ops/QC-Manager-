# 29. Cross-cutting conventions

Spec `spec-foundation-001` · compatibility: behavior-compatible · leakage review: passed

## Summary

Foundation behavior for a modular project-management web platform consisting of a Python HTTP API backend and a browser single-page frontend. Covers: process startup with background boot behind an already-open port and phase reporting; an unauthenticated health endpoint with tri-state diagnostics; a layered request pipeline (correlation id, version header, size and JSON hygiene limits, compression, locale selection, cross-origin policy, security headers, optional public-demo restrictions); a uniform error shape; typed environment-driven configuration with strict secret rules outside development; bearer-token authentication that re-reads role and permissions from storage on every request, with password-change and per-session invalidation, API-key callers and role/permission guards; a plug-in module system with dependency ordering, versioned route mounting and runtime enable/disable; an in-process event bus; sliding-window rate limiting with trusted-proxy address resolution; PostgreSQL-only persistence with per-request transactions and a pluggable local or S3-style blob store; a command-line surface; single-origin static serving of the frontend with client-route fallback; and the frontend shell (startup gate, query defaults, public versus protected route groups, persistent layout with nested error containment, project-route gate, API client conventions, language selection and account language sync, right-to-left support). Inventory-level: feature modules, menus, language catalogue content and identity, project and commercial endpoints are left to later units. No public surface items are declared (exactness is behaviour-only; standard request headers are described as behaviour claims); all other names are described neutrally and the destination chooses its own names and structure.

## Behaviour

- When started as a real server, the listening port opens immediately and startup runs in the background. Until startup ends, every API request except health receives a 503 JSON response with a human-readable detail, a machine-readable code (distinct codes for still starting versus failed startup), a boot snapshot, a Retry-After of 3 seconds and caching disabled. WebSocket connections under the API path are closed with close code 1013. Non-API requests (static files, the application shell) pass through so the browser can render a setup screen. _(ob-01; observed)_
- The boot snapshot contains: status (starting, ready or failed), current phase name, one-based step number, total step count, whole seconds elapsed since start and whole seconds elapsed in the current phase. Startup is divided into a fixed ordered list of named phases (the destination chooses the list); a phase not in the list reports step 0. _(ob-02; observed)_
- When the server is hosted in-process (tests, embedded hosts) or an explicit option requests inline boot, startup completes before the first request is accepted and nothing is gated. A separate option for test runs skips seeding and warm-up work. _(ob-03; observed)_
- If background startup raises, the state becomes failed, the failure cause is logged and emitted in a form a launcher can read, and the process asks itself to exit with a failure outcome; while it is still alive health reports a failed status with a 503. _(ob-04; observed)_
- Shutdown cancels an unfinished boot, stops all registered background processes, lets detached event subscribers finish for at most 10 seconds (cancelling and logging stragglers), tears down worker processes, closes shared outbound HTTP connection pools, disposes the database engine, and stops an embedded database cluster last. _(ob-05; observed)_
- Interactive API reference pages are served from assets bundled with the install (no third-party CDN), with operations collapsed by default. The machine-readable schema and reference pages are omitted entirely when the environment is production. The published schema reflects the current set of mounted routes, including after a module is enabled at runtime. Prebuilding the schema at startup is off by default and opt-in. _(ob-06; observed)_
- The health endpoint returns 200 with a JSON object containing: status (healthy or degraded), application version, environment name, a per-process instance identifier, counts of modules discovered, enabled and loaded, uptime in seconds, database reachability (ok or error), several tri-state diagnostics about schema consistency, whether the frontend bundle is present, current and peak process memory in megabytes (best effort) and active thread count (best effort). Tri-state means true, false or null, where null means the question was never evaluated or could not be asked. _(ob-07; observed)_
- Health status is degraded when any of the following holds: a module is enabled but not loaded; the database ping fails; a schema-consistency diagnostic reports a definite problem; the frontend bundle is missing or damaged. It stays healthy for disabled modules, for stale migration bookkeeping, and for diagnostics that themselves failed to run. _(ob-08; observed)_
- When the frontend bundle is mounted, requests to root-level probe and schema paths permanently redirect (308) to their API-prefixed counterparts so probes never receive the application shell with a success status. _(ob-09; observed)_
- Every API response carries the application version in a response header. Every request is assigned a correlation id which is echoed in a response header, attached to every log record for that request, and included in 500 error bodies and in the invalid-token message. _(ob-10; observed)_
- Text-type responses whose length is known are compressed when the client accepts it; binary exports, photos and streamed bodies are passed through uncompressed. _(ob-11; observed)_
- A global request-body ceiling (default 4 GiB, 0 disables) rejects oversized bodies before any other layer or endpoint reads them; per-endpoint upload caps remain the fine-grained limits. The destination introduces no such global ceiling (see cn-08). _(ob-12; observed)_
- JSON request bodies on POST, PUT and PATCH that contain the non-standard literals NaN or Infinity as numbers are refused with 422 and a plain detail message before reaching a handler. Tokens inside string values are not refused. Streaming responses (server-sent events) keep working. _(ob-13; observed)_
- Responses slower than 500 ms and database statements slower than a configurable threshold (default 500 ms, 0 disables) are logged at warning level. _(ob-14; observed)_
- The language of server-rendered text for a request is chosen from the Accept-Language header; regional tags resolve to their base language. _(ob-15; observed)_
- Cross-origin policy: allowed origins come from configuration (default is a single local development origin), credentials are allowed, allowed methods are GET, HEAD, POST, PATCH, PUT, DELETE and OPTIONS, allowed request headers cover content type, authorization, accept, language and a numeral-system preference, and the total-count response header is exposed to scripts. In production a wildcard origin is removed with a warning, and if nothing remains a configured public default origin is used. _(ob-16; observed)_
- In the reference behavior, requests to routes of a module hidden for the caller's market or package selection are answered with 403 by a guard that sits inside the cross-origin layer so browsers can read the refusal. Market or package based hiding is not adopted by the destination; see ob-51 for the destination behavior. _(ob-17; inferred)_
- Read-only public demo mode (default off): any request that would change persistent state is refused with 403 and a JSON body carrying a dedicated machine-readable error value plus a message. The refusal is decided before authentication and tenant lookup so anonymous callers also get 403 rather than 401. Reads and sign-in continue to work. A second, database-level layer refuses writes that slip through and answers with a byte-identical body, including when the driver wraps the error. _(ob-18; observed)_
- No-upload demo mode (default off): every multipart or octet-stream request is refused with 403 and a dedicated machine-readable error value. A retention sweep for visitor uploads (default 0 days = keep forever) only runs when read-only demo mode is also on and never removes seeded demo content. _(ob-19; observed)_
- The module system discovers modules that each carry metadata (unique name, semantic version, display name with optional per-language names, description, author, category label, hard dependencies, optional dependencies, auto-install and enabled flags, and a served-markets list where a wildcard means all). Modules load in dependency order. A module may contribute routes, data models, event subscribers, validation rules and an optional startup action. _(ob-20; observed)_
- Module failure policy: a failure in a shipped module aborts startup; a failure in an installed (third-party) module unmounts what it mounted, drops tables it created, records the reason, marks it off persistently, and startup continues. A module whose dependency failed is skipped (installed) or aborts startup (shipped). Persisted off-state is honored at boot for non-core or non-shipped modules only. _(ob-21; observed)_
- Runtime enable adds the module's routes to the live server and registers its permissions; runtime disable fails when other enabled modules depend on it; both require a dedicated permission that only administrators hold by default and respond 400 with a message on domain errors and 404 for unknown modules. Enabling an archive-installed module creates its missing tables additively. Module switches are mirrored into the caller's package selection state so the visibility guard agrees with the module list; the list reports a package-hidden module as disabled with a flag stating that a package blocked it. _(ob-22; observed)_
- A module that was enabled by an operator but failed to import at runtime stays reported as enabled-but-not-loaded, its endpoints answer 404 until restart, and health reports degraded. _(ob-23; observed)_
- The in-process event bus lets modules publish named events (hierarchical dotted names) with a data dictionary and lets other modules subscribe by exact name or with a wildcard. Handlers may be synchronous or asynchronous. Each published event has a unique id, timestamp and optional source module. Publishing returns a result listing handler results and per-handler errors; a handler failure is isolated and does not stop other handlers. Detached side-effect tasks are tracked so they are not lost and failures are logged at warning level. _(ob-24; observed)_
- Roles are hierarchical: administrator above manager above editor above viewer; three field-site roles rank at or below viewer with an initially empty permission set. Legacy and trade titles are aliases that resolve to a canonical role. Permissions are named module.action, each with a minimum role; modules register theirs at load and unregister them on removal, keeping any permission still owned by another module. An unknown permission is denied to everyone below administrator. _(ob-25; observed)_
- Rate limiting uses in-memory sliding windows (60 seconds unless stated) keyed per user or per client address, with separate limits per traffic category. Reference defaults: login 10 per window per address, AI requests 20 per window per user, anonymous account creation 20 per hour per address, uploads 30 per window per user; other categories (general API, approvals, device ingest, public share links with an additional per-link ceiling) have their own limits. Several limits are configurable. A per-API-key limiter honors each key's own limit. _(ob-26; observed)_
- Persistence is PostgreSQL only, through a pooled asynchronous engine with configurable pool size, overflow, connection recycling, liveness check on checkout and idle-in-transaction cutoffs (separate for requests and background jobs, 0 disables). A non-PostgreSQL or empty URL makes engine creation fail. Each request obtains a session that commits on success and rolls back and re-raises on error; objects stay readable after commit. The reference behavior starts an embedded PostgreSQL cluster in the data directory by default when no external URL is given; the destination does not manage an embedded cluster (see cn-03). _(ob-27; observed)_
- Binary content is stored through a backend-agnostic blob store offering put, streaming put, get, exists, delete, delete by prefix, size, prefix listing, streamed read, optional downloadable URL, optional local path, and multipart upload (initiate, upload part, complete, abort, signed part and put URLs). Two backends exist: local filesystem and S3-compatible object storage selected by configuration. Keys are normalized to prevent escaping the storage root. Large uploads go directly to object storage in parts with a bounded number of concurrent initiations (default 8) that answers 429 when full, and a ceiling on proxied fallback uploads. _(ob-28; observed)_
- When a frontend bundle is found, the server serves hashed assets with a one-year immutable cache policy and everything else with revalidation; unmatched non-API paths receive the application shell with status 200 so client-side routes work on reload; unmatched API paths receive the normal JSON 404; unmatched paths that look like files (known static suffix or under the assets path) receive a real 404 instead of the shell. When no bundle is present, non-API unmatched paths receive a 404 whose message explains that this server was shipped without a user interface. _(ob-29; observed)_
- Backend language routes: list available languages; list, per printed form, the languages it can be rendered in; return the full message map for a language. Regional codes resolve to their base language. The response carries a meta block with the requested locale, a fallback flag (true when English is served instead of the asked language), the fallback language when applicable, and the resolved language when it differs from the request. _(ob-30; observed)_
- Frontend bootstrap behavior: any demo selection in the URL is captured, stored display preferences (desktop text-scale, unit system) are applied, stale-chunk recovery and account-language sync are active, obsolete offline caches are retired in the background, and the application is wrapped by the startup gate and mounted under a base path when served under a sub-path. Mounting waits for a saved non-English language chunk (at most 2 seconds) and for the desktop text-scale reply (at most 300 ms), then mounts regardless; English boots mount synchronously. _(ob-31; observed)_
- Server-starting gate: probes the health endpoint without cache; a 2xx lets the application render; a 503 with a boot body shows a full-screen setup screen with the current phase label, a progress percentage derived from step over total steps, a locally ticking elapsed clock, and a failed variant explaining that startup stopped and to restart after reading the server log; when the probe cannot be reached at all it fails open and renders the application. Polls every 2 seconds; the first check may hold the application back for at most 1.5 seconds. The setup screen is announced as a polite live status region. _(ob-32; observed)_
- Query client defaults: data fresh for 2 minutes, cached 5 minutes after unmount, offline-first network mode, no refetch on window focus, at most one retry and none when offline, on client timeout or abort, or on any 4xx response; mutations are never retried and are queued while offline then replayed on reconnect. After any successful mutation carrying a key, queries sharing that key's first element are invalidated. Query and mutation failures are reported by global toast handlers that stay quiet when the screen reports the failure itself. _(ob-33; observed)_
- When a new build is deployed while a tab stays open and a lazy chunk fails to load, the app reloads once to fetch the current build; a timestamp guard prevents repeated reload loops during a real outage. _(ob-34; observed)_
- Routing: public routes render without the application layout. The sign-in, registration, forgot-password and alternate sign-in routes show the destination home when already authenticated. Password-reset completion and email-verification routes render regardless of authentication (reset must not be redirected away and must not sign the user out on arrival). The onboarding wizard is full screen, requires authentication and has no layout. All other routes sit under one persistent layout that requires authentication; the root path sends an authenticated user to the configured landing page. Legacy paths may permanently redirect to consolidated pages. Unknown paths show a not-found page for authenticated users and redirect to sign-in for others. Additional routes are generated from the module registry and wait for the per-account enabled-module list to load. _(ob-35; observed)_
- Authentication gate: an unauthenticated visit to a protected route redirects to the sign-in route (replacing history) with a return-to query parameter holding the original path and query, omitted when the path is the root. After sign-in the user lands at that destination. _(ob-36; observed)_
- Persistent layout: the navigation and header regions mount once per signed-in session and only the page area swaps on navigation. Each page area is wrapped in an error container keyed by the current path so a crashed page recovers on the next navigation while the layout stays; the layout itself has an outer container whose recovery action reloads the whole document. The outer container sits inside the authentication gate so a signed-out visitor never sees a recovery card in place of the redirect. Page loading shows a skeleton placeholder; first paint of the app shows a loading screen; while a new tab waits for another tab's session answer, only a loading screen is shown. _(ob-37; observed)_
- Project route gate: a page under a project-scoped path looks up the project once (shared with the project page); only a 404 answer replaces the page with a single not-found message explaining the project does not exist or access was lost, plus a primary action leading to the project list, and clears the stored active project if it is that one. Loading, other errors and success render the page unchanged. The lookup never retries on 4xx and retries once otherwise. _(ob-38; observed)_
- Layout regions: a fixed navigation sidebar on wide screens (anchored to the start side of the reading direction); on narrow screens it is a slide-in drawer opened by a header menu control or an edge swipe and closed by tapping the dimmed overlay or swiping, with background scroll locked while open and swipe directions mirrored in right-to-left. On narrow screens a bottom navigation bar offers an action that opens the drawer, and page content has bottom padding that keeps it clear of floating controls. Progress indicators for background tasks, uploads and conversions persist across navigation. _(ob-39; observed)_
- Document title is the translated page title followed by a separator and the workspace brand name (the user-configured company name when set, otherwise a default application name), or just the brand when there is no page title; it re-translates when the language changes. Offline edits are replayed when connectivity returns. _(ob-40; observed)_
- Workspace branding is pulled from the server (public endpoint) after load and after authentication changes, painting first from local storage; account preferences, the saved custom unit catalogue, collapsed info-card state and the enabled-module list are pulled only once authenticated. A first-run guided tour starts once per browser and can be relaunched on request. _(ob-41; observed)_
- API client conventions: all calls go to a fixed base path; every request sends Accept as JSON unless overridden, the bearer token when present, the primary language subtag as Accept-Language unless caller-set, and the numeral-system preference when not automatic. Default abort timeouts are 90 seconds for reads and for mutations and 5 minutes when a call opts into long-running, with an explicit per-call override; a timeout raises an error flagged as a timeout and at most one timeout toast is shown per 30 seconds. Helpers cover get, post, patch, put, delete, authenticated raw fetch, and authenticated file download. _(ob-42; observed)_
- On a 401 from a protected call, the client silently refreshes the access token and replays the original request exactly once; auth endpoints themselves never trigger this. If the refresh token is refused, all tabs sign out and the user is taken to sign-in; if the refresh failed only transiently (deploy, network) the session is kept and the error surfaces. A second 401 after a fresh token is a real failure. Permission-denied 403 answers do not end the session. _(ob-43; observed)_
- Client error objects carry status, status text and the raw body, with a user-friendly message taken from the body (plain detail string, validation list, message or error field, short plain text up to 240 characters) or else from a per-status fallback translated through the language layer (400, 401, 403, 404, 409, 413, 422, 429, 500, 502-504, other 4xx, other 5xx, unknown). Demo refusals use dedicated translated messages instead of the server text. _(ob-44; observed)_
- Paged list results come in two conventions: a body envelope with items, total (rows matching the filter, not the page size), offset and limit; and a bare list with the total in a response header. The client treats total greater than the number of items as truncated and surfaces it. For new list endpoints the destination uses only the body envelope, with items, total, page and page size (see ob-53). _(ob-45; observed)_
- Frontend supported languages are a fixed list of about fifty entries, each with a code, native name, English name and a country code (plain English maps to a not-tied-to-a-market country code). It includes regional variants of English (UK, US), Spanish (Mexico, Chile, Colombia), Portuguese (Brazil) and Traditional Chinese (Hong Kong), and four right-to-left languages (Arabic, Urdu, Persian, Hebrew). English ships in the main bundle as the fallback; every other language is fetched on demand as a separate chunk, once, and regional variants hold only the words they name differently with the rest answered by the base language. Some languages are deliberately not offered until review. _(ob-46; observed)_
- Language matching for a BCP-47 tag normalizes underscores, tries the exact region, then day-first English regions (a listed set of non-US English-speaking regions) map to British English, Traditional Chinese tags (script Hant, or regions HK, MO, TW without a Hans script) map to the Hong Kong entry and never to Simplified, otherwise the base language if shipped, else nothing. A partner pack's default language is normalized with the same rule, falling back to English. Country detection uses only the region subtag of the browser language (falling back to other listed browser languages of the same base language, then to the country declared for the chosen UI language); it is an offer hint, never a gate. _(ob-47; observed)_
- Account language sync: a language picked while signed in is saved to the account profile with a plain, silent request (a refused write on a read-only demo must not show a not-saved dialog and failures are ignored). After sign-in on a browser that holds no language choice, the account's saved language is applied if it is supported and differs from the one on screen; the default value of English is never restored because it says nothing about the person's choice. A choice made in this browser always wins over the account. Languages applied automatically (pack defaults) are not recorded as a person's pick. _(ob-48; observed)_
- Document direction (left-to-right or right-to-left) follows the active language, and layout side placements (sidebar, swipe gestures, logical start/end spacing) mirror accordingly. _(ob-49; observed)_
- Authentication state: tokens are kept in persistent storage when the user chose to be remembered and in per-tab session storage otherwise; a session-only sign-in is shared with other tabs of the same origin through a broadcast channel handshake (a brief wait for existing tabs to answer) and nothing secret is written to persistent storage for it. A refresh keeps whichever storage the session used. The display name is cached so a reload paints it before the profile arrives. _(ob-50; observed)_
- A module that is switched off, globally or for a project, answers not-found automatically for its routes, and the frontend hides its menu entries. Market or package based hiding of modules is not added. _(ob-51; derived)_
- The destination event bus calls matching handlers one after another in registration order and waits for each to finish. A failing handler is logged and does not stop the remaining handlers, and there are no retries. Work that must survive a restart is handed to the background task queue instead of a bus handler. _(ob-52; derived)_
- New list endpoints return the paginated body envelope with items, total, page and page size, as the destination's listing rule requires. No count-header pagination convention is added. _(ob-53; derived)_
- Each frontend module declares its routes, menu entries and permissions in its own manifest, and the menu follows the backend module switches. New quality screens register in this way. Workspace profiles and menu personalization are not changed. _(ob-54; derived)_
- Background and scheduled work uses the destination's existing task queue, with optional cron schedules declared by each module. The quality slice adds no scheduled work. _(ob-55; derived)_
- Requests to protected routes carry a standard bearer credential header, and a missing or unusable credential is answered with the standard 401 challenge. Clients and integrations rely on this standard scheme; the destination already handles it. _(ob-56; observed)_
- The preferred language for server-rendered text and localized catalogue values is taken from the standard language-preference request header, and the frontend sends the primary language subtag of the active language on every call. The destination already handles this header. _(ob-57; observed)_

## Inputs

- Configuration is read from process environment variables (case-insensitive) and from dotenv files located independently of the working directory. Process environment wins over dotenv. Unknown keys are ignored. Typed validation rejects bad values at startup, except AI timeouts which are clamped into a bounded range. _(in-01; observed)_
- Behavior-relevant configuration groups and defaults: environment (development, staging, production; default development); debug off; log level info; allowed origins; trusted proxy ranges (default loopback and private ranges); extra content-policy connect origins (https hosts and local http only, others dropped); allowlists for self-hosted AI endpoints and for webhook destinations (empty means webhooks may not reach loopback, private or other non-global addresses, and link-local and cloud-metadata addresses are always blocked); database connection settings including slow-query threshold and maximum batch size 1000; storage backend selection with S3-style parameters; large-upload tunables; request body ceiling; token signing secret, HMAC-SHA-256, access lifetime 60 minutes, refresh lifetime 30 days, previous secrets for rotation; single-sign-on settings (issuer, client, scopes, auto-create users on, group-to-role map, role claim paths, default role viewer, enforced email domains); registration mode (default approval-required) and default registration role (viewer, never administrator); tenant row-level isolation (off); demo read-only, upload blocking and retention (off, off, 0); email backend options (console, SMTP, no-op, in-memory; default console), SMTP settings, daily email caps per recipient 20 and per instance 300; rate limits. Settings belonging to feature modules are covered by later units. _(in-02; observed)_
- Database URL forms: any postgres-style URL (with or without a driver) is rewritten to the asynchronous driver form for the engine and the synchronous form for tooling; when only one of the two is given the other is derived; when none is given but password and host parts are supplied through separate settings (user, password, host, port, name) a URL is composed with percent-encoding, and also replaces a supplied URL whose host contains an at-sign (a password that was not encoded). Non-PostgreSQL schemes pass through untouched. _(in-03; observed)_
- Command-line server arguments: bind host (default loopback), bind port, data directory, embedded-database flag (default behavior), open-browser, quiet, and mutually exclusive demo-on/demo-off flags; the demo-off choice is persisted in the data directory and the demo-on flag clears it. A top-level version flag prints the same report as the version command. _(in-04; derived)_
- Protected API calls present credentials as a bearer token; routes that opt in additionally accept an API-key credential header from headless callers, where the bearer token takes precedence when both appear. _(in-05; observed)_
- Frontend inputs persisted in the browser: tokens and remember-me choice, selected language, desktop text-scale, module enablement, branding cache, onboarding and tour flags, review-prompt counters, menu layout and view-mode preferences; the application base path is derived from the URL when served under a sub-path. _(in-06; observed)_

## Outputs

- Success health body: JSON object with the fields listed in the health behavior; starting or failed health body: JSON with status, version and a boot block, status 503, Retry-After 3, no-store. _(out-01; observed)_
- Module list rows include name, version, display name, per-language display names, description, author, category, enabled, loaded and package-block flag; detail and dependency-tree responses exist per module name. _(out-02; observed)_
- Language catalogue responses: a languages object with the available list; a forms object mapping each printed form to its language codes; and a flat message map plus the meta block described above. _(out-03; observed)_
- API-key calls on rate-limited keys return remaining and total counters in rate-limit response headers. _(out-04; observed)_

## States and transitions

- Boot state moves starting to ready, or starting to failed, once per process; ready opens the API gate; failed keeps it closed and ends the process. _(st-01; observed)_
- Module state: discovered, ordered, loaded and mounted; or failed (recorded, persisted off for installed modules). Runtime enable moves a module to loaded with routes added; runtime disable removes it and persists the off state; a failed runtime enable leaves it enabled-but-absent. _(st-02; observed)_
- A password change sets a per-user credential cutoff time; every credential issued before it (to whole-second resolution) stops working on HTTP and websocket entry points alike. A revoked session stops working while the person's other sessions continue. _(st-03; observed)_
- Frontend session: signed out to signed in on credential receipt (all gated effects such as preference, brand, module and unit sync start then); signed in to signed out on refresh rejection or explicit logout across all tabs; module-enablement flag resets on sign-out. _(st-04; observed)_

## Timing and ordering

- Request pipeline ordering requirements: the startup gate runs before everything else; the upload block and body-size ceiling run before any layer or endpoint reads the body; the correlation id is bound before audit context so the id is available there; the module visibility guard sits inside the cross-origin layer so its refusals carry cross-origin headers; for route-level dependencies the read-only-demo guard runs first, then tenant context binding. _(to-01; derived)_
- Startup order: configuration and logging; strict secret validation; translations; database connection and schema preparation; module discovery and ordered load; validation registration; demo and reference seeding (inline or background per options); optional index warm-up; schedulers and sweepers; route-table warm-up before the API opens. _(to-02; derived)_
- Between module imports during background boot the server yields briefly so queued health and static requests are answered. _(to-03; observed)_
- Shutdown order: cancel boot, stop background processes, drain event subscribers (max 10 s), stop worker processes, close outbound pools, dispose engine, stop embedded database. _(to-04; observed)_
- Rate-limit windows slide over the previous 60 seconds (3600 for the hourly account-creation cap); idle bucket keys are swept at most once per window. _(to-06; observed)_
- Frontend ordering: the saved-language chunk and desktop text-scale reply gate first paint (caps 2 s and 300 ms); health polling every 2 s; the account language is restored at most once per session after sign-in unless the browser already holds a choice. _(to-07; observed)_

## Edge cases

- Legacy tokens without a type claim are accepted as access tokens only; tokens without a session id are honored but cannot be revoked individually; a session id with no stored record is honored (fail-open, justified by database restores), logged once per distinct session using a bounded memory. _(ec-01; observed)_
- A token minted within the same second as a password change is treated as newer and survives; a token with no issued-at claim skips the cutoff comparison. _(ec-02; observed)_
- Client address resolution believes forwarding headers only when the direct peer lies inside the trusted-proxy ranges; the forwarding chain is read from the right, skipping trusted hops, and the first untrusted address wins; if all hops are trusted the leftmost is the client; a real-IP header is the fallback; unparsable peers are untrusted; no peer yields an unknown identifier. _(ec-03; observed)_
- Optional-authentication routes accept requests with no credentials, with invalid credentials treated as absent, or with valid credentials. _(ec-04; inferred)_
- Traditional Chinese readers (tags with Hant script or HK, MO, TW region without Hans) are never answered with the Simplified entry; they receive the Hong Kong entry, or English when absent. A three-part tag such as language-script-region resolves via its region or base language. _(ec-05; observed)_
- A language code and a region code that happen to share the same letters are separate namespaces; nothing may derive a UI language from a region code. _(ec-06; observed)_
- While the server is not yet reachable or answers with something other than a boot body, the frontend renders as normal rather than blocking on the setup screen. _(ec-07; observed)_
- Backend language routes accept regional or base locale codes interchangeably, resolving regional codes to the base language. _(ec-08; observed)_
- A database password containing special characters supplied only as parts is percent-encoded so host parsing is unaffected; a supplied URL damaged by an unencoded at-sign is replaced by the composed one when parts are present. _(ec-09; observed)_

## Errors

- Any unhandled server exception produces status 500 with a JSON body holding a generic detail message and the correlation id, plus the correlation header; no exception text or stack trace reaches the client and the full trace is logged with the same id. _(er-01; observed)_
- A request that fails validation only in path parameters answers 400 with a body holding a generic error value and no detail (unless debug is on). Failures in body, query or header answer 422 with a detail list of error entries; outside debug the echoed offending input is removed from each entry; non-serializable context values are coerced to text. _(er-02; observed)_
- Business and authorization errors use a JSON body with a detail string; demo refusals and some other cases use an error value plus message; startup refusals use detail, a machine-readable code and a boot block. _(er-03; observed)_
- Authentication failures: no credentials gives 401 with a Bearer challenge header and a not-authenticated message; a bad, expired or wrong-type token gives 401 with a generic message (never library internals) that includes the correlation id; a token with no subject, an unknown or deactivated user, a token older than the last password change, or a revoked session each give 401 with a distinct plain message; if the user store cannot be reached the request is refused with 503 (fail closed) and never trusts token claims. _(er-04; observed)_
- Authorization failures give 403: a missing permission names the permission, a role guard names the required role, an API key lacking the permission says so. Denials are logged only at debug level to avoid noise. In read-only demo mode a defined set of read-grant permissions is let through even if the role lacks them. _(er-05; observed)_
- Exceeding the AI limit gives 429 with a message and Retry-After of 60 seconds; other limiters report remaining allowance and a retry-after computed from the oldest request in the window (minimum 1 second). _(er-06; observed)_
- Module API: unknown module gives 404 with the module named; enable or disable domain failures give 400 with the message. _(er-07; observed)_
- An unsupported locale on backend language routes gives 404 with a message listing supported codes. _(er-08; observed)_
- Startup refuses to proceed outside development when the signing secret is a published or boilerplate value or shorter than 32 characters or 32 bytes (the stricter wins); a non-PostgreSQL database URL fails engine creation with a message naming PostgreSQL. _(er-09; observed)_
- Frontend maps API failures to translated, user-friendly messages by status and surfaces them as toasts or dialogs; timeouts are described as slow requests that were cancelled; conflict, payload-too-large and rate-limit have their own wording. _(er-10; observed)_

## What it must not do

- The unauthenticated health endpoint never exposes exception text, statement text, module names, repair identifiers or column names; only booleans, counts and fixed vocabulary. _(ng-01; observed)_
- In production the machine-readable schema and interactive reference pages are not served. _(ng-02; observed)_
- Self-registration default role and the single-sign-on default role can never be administrator; automatic administrator creation only occurs for the very first registrant when no administrator exists. _(ng-03; observed)_
- Role and permission claims inside a token are never trusted; forged claims have no effect. _(ng-04; observed)_
- Response serialization must tolerate non-finite floats emitted by data pipelines without failing the response. _(ng-05; observed)_
- Asset requests that miss are never answered with the application shell and a success status; stale hashed bundles must produce a true 404. _(ng-06; observed)_
- The company letterhead profile is never exposed through the anonymous branding read; it has its own protected route. _(ng-07; observed)_
- No third-party font hosts are used; typefaces are served from the application itself and the content policy lists no font host. _(ng-08; observed)_

## Security

- Access and refresh credentials are signed tokens (HMAC-SHA-256 by default) with a type claim; only access-type tokens reach protected routes. New tokens are always signed with the current secret; a comma-separated list of earlier secrets is accepted for verification only, to allow rotation without logging users out. _(sec-01; observed)_
- On every protected request the user's role and permission list are reloaded from storage and replace token claims; deactivation, demotion and permission changes take effect immediately. A stale token carrying an older permission list is still honored through the live role-to-permission mapping. _(sec-02; observed)_
- Administrators pass permission checks; others need the named permission. A separate role guard rejects anyone below a required role and is used on destructive operations such as database wipes. API-key authority is the intersection of the owner's live permissions and the key's declared permission list; the narrowing runs before the administrator bypass so an administrator's key can be restricted. _(sec-03; observed)_
- Registration modes: open, verification-required (currently behaves like approval-required), approval-required (new accounts inactive until an administrator activates them; default) and closed (self-registration refused). The first registrant when no administrator exists bypasses the gate and becomes administrator. Email domains configured as single-sign-on-only refuse password sign-in, registration and password reset with 403 and a fixed error key, except for an administrator flagged as break-glass. _(sec-04; observed)_
- Response headers on every response: frame embedding only from same origin, content-type sniffing off, referrer only same-origin, camera, microphone and geolocation disabled, strict transport security only for HTTPS requests in production, a restrictive content security policy (self by default, script and style relaxed for the single-page app, no third-party hosts listed (the destination adds none; see sec-13), same-origin and data/blob frames for in-app document previews), and the server banner header removed. _(sec-05; observed)_
- Outbound request policy: self-hosted AI endpoints may use loopback and private addresses by default but link-local and cloud-metadata addresses are always blocked, optionally narrowed to an allowlist; webhooks default to refusing every non-global address unless allowlisted; extra connect-source origins must be https hosts or local http. _(sec-06; observed)_
- Abuse limits: login attempts 10 per minute per address, anonymous account creation and magic-link requests 20 per hour per address (so taken-email answers cannot sweep address lists), uploads 30 per minute per user, share-link password attempts limited per address and per link token, device ingest limited per address. _(sec-07; observed)_
- A development-only switch that returns magic-link tokens and PINs in responses and logs reset URLs is separate from debug and never honored in production. _(sec-08; observed)_
- Multi-tenant row-level isolation is an opt-in setting (default off): when on, each request binds the caller's tenant for the database session so tenant-owned tables fail closed; anonymous callers bind no tenant; shared reference data is never tenant-scoped. _(sec-09; observed)_
- Intentionally public endpoints include health, the licence and disclosure notice, workspace branding read, bundled third-party licence texts and backend language catalogues; write operations on branding are administrator-only. _(sec-10; observed)_
- Frontend credential handling: bearer token attached automatically; session-only sign-ins live in per-tab storage and are shared across tabs only through a same-origin broadcast handshake; raw-fetch helpers share the same single refresh-and-replay behavior; HTML content from users is sanitized before display. _(sec-11; observed)_
- High-value actions are recorded in the destination's append-only audit ledger in the same transaction as the change, so the entry and the change are committed or rolled back together. Every route checks project visibility. The quality slice uses these as they are and adds no tenant isolation or cost attribution behavior. _(sec-12; derived)_
- The destination's security headers list no third-party hosts, and the quality slice adds none. _(sec-13; derived)_

## Invariants

- Health is always answerable without credentials, in every boot state, and always reflects what this process serves rather than what disk currently holds. _(inv-01; observed)_
- Tri-state diagnostics never turn an unknown (null) into a reassuring false or an alarming true; each diagnostic answers exactly one question and a failure of a diagnostic never degrades status. _(inv-02; observed)_
- A paged list's total counts rows matching the filter, never the page length. _(inv-03; observed)_
- One correlation id per request is used consistently in logs, response header and error body. _(inv-04; observed)_
- Each module's routes are reachable only under the versioned prefix with its hyphenated name; permissions of an unloaded module are not offered or enforced. _(inv-05; observed)_
- The application layout is mounted exactly once per signed-in session; a crash in a page never removes the layout, and a crash in the layout never shows a recovery card to a signed-out visitor. _(inv-06; observed)_
- Every user-facing string resolves through the language layer with English as the final fallback; a language chosen in this browser always outranks the account's saved language; nothing becomes unreachable because a country guess was wrong. _(inv-07; observed)_
- The weak-secret rule and the minimum secret length are defined once and applied uniformly by every component that checks secrets. _(inv-08; observed)_
- Diagnostic state belongs to each application instance, so a second application in the same process never inherits the first one's verdicts. _(inv-09; observed)_

## Notes

- Compatibility target is behavior-compatible on observable behavior only (health semantics, versioned prefix convention, error codes and shapes, role hierarchy, module API semantics, language routes, sign-in redirect). Only standard protocol header names are retained by name; every other path, header, config key, error value and role name is described neutrally and the destination may choose its own names. Feature changes elsewhere are permitted; the clean design may reorganize modules, menus and internals freely. _(cn-01; derived)_
- Data store: the reference behavior supports PostgreSQL only and bundles an embedded cluster. The destination already uses PostgreSQL through a configured database server and does not manage an embedded cluster; no embedded cluster and no alternative store are added. Embedded-cluster options, startup and shutdown steps described elsewhere in this spec (command-line embedded-database flag, last-step cluster stop, default embedded start) are therefore not required. _(cn-03; derived)_
- The origin publishes a machine-readable schema in non-production and generates typed frontend client definitions from it; the frontend API client is generic and typed by response type. _(cn-04; observed)_
- Numeric defaults (timeouts, limits, lifetimes, pool sizes) listed in this spec may be re-tuned by the destination as long as the corresponding configuration knobs exist and defaults are recorded. _(cn-06; inferred)_
- The destination's own conventions take precedence over this spec for routing, configuration, error shape and readiness reporting; this foundation spec is used only as background. Modules are mounted under a versioned path prefix and follow the destination's module contract. _(cn-07; derived)_
- No new global request-body ceiling is introduced. The destination's existing upload and request handling continues unchanged, so no new refusal status or body is defined. _(cn-08; derived)_
- Rate limiting stays with the destination's authentication layer, whose backend is chosen by configuration. The quality slice adds no new limiter. _(cn-09; derived)_
- Each module keeps its own English message catalogue read through the destination's translation layer. No catalogue completeness thresholds are introduced for the quality slice. _(cn-10; derived)_

## Non-goals

- No implementation code, framework choice or source layout is prescribed by this foundation spec, and the destination is not asked to mirror any origin structure, naming or file organization.
- Desktop packaging, native launcher integration and the desktop-only toolbar are out of scope unless approved at the scope gate.
- Boot-time schema healing, data-repair ledgers and migration-stamp diagnostics are origin-specific upgrade mechanics; the destination may use ordinary versioned migrations while keeping the health vocabulary only where chosen.
- Do not reproduce origin provenance markers.
- Content of feature modules, navigation menus, menu personalization, product tour steps and every language's message text are covered by later units, not here.
- Vector search, embedding and AI provider integrations are not specified here beyond configuration inputs.
- Demo content, demo accounts and their credentials are not reproduced.
- The quality slice adds no live-connection or presence behavior; the destination's existing authentication is unchanged.
- The quality slice adds no offline queueing or replay behavior; the destination's current behavior is unchanged.
- The quality slice adds no new upload or storage mechanism; attachments continue to use the destination's existing file handling.
- No external update check is added; the destination makes no such call and the quality slice does not introduce one.
