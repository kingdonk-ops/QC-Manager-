# 13. BCF issue exchange

Spec `spec-bcf-exchange-001` · compatibility: behavior-compatible · leakage review: passed

## Summary

Issue exchange with BIM tools through the open BCF format. A project keeps a register of BCF topics with comments and viewpoints (camera, component selection and visibility, optional snapshot image) that can be created and edited in the application, exported as a BCF archive in version 2.1 or 3.0 (whole project or a chosen subset), and imported idempotently from an archive of either version with a structured report of problems. Separate paths exchange clash results as BCF 3.0 topics (export, and idempotent import that updates existing clash issues) and punch items as BCF topics. A REST profile of the open BCF API 3.0 standard gives BIM tools live access with concurrency control. Reading is defensive against hostile archives. Imported content is limited to what the application models; unmodelled fields are not guaranteed to round-trip. Numeric limits, caps and thresholds in this spec are illustrative parameters; the destination chooses its own values. BCF 2.1, BCF 3.0 and the BCF API 3.0 are public standards and their element and operation names may be used for interoperability.

## Behaviour

- The BCF archive is a zip with a version marker, an optional project information document, and one folder per topic holding a markup document, one viewpoint document per viewpoint and optionally a snapshot image. Both BCF 2.1 and 3.0 are produced and read. The layout is the same in both; the markup differs as the standards define: in 3.0 comments and the viewpoints list sit inside the topic element (comments optionally in a container) and the topic carries a server-assigned identifier attribute, while in 2.1 comments and viewpoints sit beside the topic element and the topic carries an index element. The 2.1 version marker also names a detailed version; the 3.0 one does not. Viewpoint documents carry their identifier only in 3.0. _(bcf-beh-001; observed)_
- Exchanged topic data: identifier (GUID), type, status, title, priority, stage, index or server-assigned identifier, assignee, due date, labels, reference links, creation author and date, modification author and date, description, comments (identifier, date, author, text, modification author and date, optional link to a viewpoint) and viewpoints (identifier, perspective or orthogonal camera with position, direction and up vector plus field of view or view-to-world scale, selected components, visible or hidden components by IFC identifier with a default-visibility flag, line markup, clipping planes, optional snapshot image). Labels are repeated elements in 2.1 style and may also be nested in a container in 3.0 style when reading. Dates are written in UTC with a literal Z suffix; when reading, a missing zone is taken as UTC and a date without time is read as midnight UTC. _(bcf-beh-002; observed)_
- Visibility encoding in viewpoints: a default-visibility flag plus an exceptions list. When default is visible, the exceptions are the hidden components; when default is not visible, the exceptions are the visible components. The 3.0 writer for clash exports always emits the shorter of the visible and hidden lists as the exceptions and flips the default to match; the register export writes the stored default with the matching list. Selection components are always emitted when present. Exactly one camera kind is written per viewpoint. _(bcf-beh-003; observed)_
- Project register export takes a target version (2.1 by default, or 3.0); any other version is refused with a validation error that lists the supported versions. A second export form takes a body with a version and an optional bounded list of topic identifiers (illustratively up to one thousand): omitted means the whole project, a list that matches nothing is refused with a validation error instead of producing an empty archive, and the response carries a header with the number of topics written. The download file name includes the project, the scope (all or selection) and the version. Snapshot images are included when their stored blob exists; a missing blob does not fail the export, the viewpoint is written without an image. _(bcf-beh-004; observed)_
- Project register import takes a file and an optional forced version. The version is detected from the version marker (or its detailed-version child); if absent or unreadable the archive is assumed to be 2.1 with a warning; an unsupported version is an error. Topics, comments and viewpoints are matched by their GUID within the project: an unknown GUID creates a record (missing title becomes a placeholder, missing status becomes open, record flagged as imported), a known GUID is overwritten in place field by field. Comments are matched by GUID within their topic (a missing GUID gets a new one), viewpoints likewise, and snapshot images are stored and attached. Importing the same archive twice therefore leaves the same data. _(bcf-beh-005; observed)_
- Import never fails with a server error for content problems. It returns a report with an overall status (passed, warnings or errors), the detected version, counts of topics created, topics updated, comments created and viewpoints created, and a list of findings each with severity (error, warning, info), a short code, a message and optionally a location. Findings include: not a zip or corrupt zip (error, nothing imported); entry with an unsafe path (warning, entry skipped); single entry above a size limit, too many entries or total uncompressed size above a cap (errors; illustrative caps of tens of thousands of entries and about one gibibyte); unsupported version (error); no markup documents (error); a topic markup that is malformed or lacks a topic or GUID (error); a referenced viewpoint document that is missing or malformed (warning); a missing snapshot (info); a topic with no GUID (warning, skipped). If any error-level finding exists after parsing, the whole import is abandoned and nothing is written, so one malformed topic blocks the others (see decision points). _(bcf-beh-006; observed)_
- Upload handling for register import: an empty body is a client error, an unreadable body is a client error, and a body above a configurable size cap is refused as too large. Messages are returned in the caller's language. _(bcf-beh-007; observed)_
- Topic maintenance in the register: creating assigns a fresh GUID, records the caller as creation and modification author with the current time, defaults status to open and keeps optional type, priority, stage, assignee, labels, reference links, due date and a model association; updating applies only supplied fields and stamps modification author and time; deleting removes the topic with its comments, viewpoints and stored snapshots (blob deletion is best effort). Adding a comment records author and time and may reference a viewpoint of the same topic (an unknown viewpoint is refused); editing a comment replaces its text and stamps modification author and time; adding a comment also stamps the topic as modified. Adding a viewpoint takes one camera kind, component data, element identifiers and an optional base64 PNG (a data-URL prefix is tolerated, invalid base64 or non-PNG content is refused); viewpoints get an increasing index within the topic. A topic can be addressed by its internal identifier or by its BCF GUID, and an identifier belonging to another project does not resolve. _(bcf-beh-008; observed)_
- Clash export builds a BCF 3.0 archive from a project's clash results with optional filters on status (a special value open expands to all unresolved states) and severity. Each topic uses the clash's stable signature as its GUID (a fresh GUID when the signature is empty), topic type clash, status and priority mapped from the clash status and severity, a title made of the two element names and the clash type truncated to a bounded length (illustratively a few hundred characters), a description listing the two disciplines (unassigned when missing), clash type, penetration and distance in metres to four decimals and the signature, labels of clash type and severity, assignee and due date when present, and, when the clash has a non-zero centroid, a synthesized perspective viewpoint positioned a short fixed offset (illustratively a few metres) back from and above the centroid looking at it. Results that recur across runs with the same signature are emitted once, keeping the newest. Topic GUIDs are validated before use as folder names (UUID or hex signature), so a hostile title can never escape the archive. When clash storage is unavailable the export answers service-unavailable. _(bcf-beh-009; observed)_
- Clash import accepts only BCF 3.x archives from any tool. Each topic is matched to an existing clash issue first by server-assigned identifier and then by signature (the topic GUID when it is itself a valid hex signature, otherwise a stable hash derived from it). A new topic creates an issue with mapped status, mapped priority, labels as tags and a weak signature quality; an existing issue gets status, priority and tags updated and its last-seen marker advanced, while its assignee and due date are left alone. Status mapping: open and reopened map to the initial new state, in progress maps to the ongoing existing state, closed maps to resolved, with the application's own status words accepted; priority mapping: critical to critical, major or high to high, normal or medium to medium, minor or low to low; unknown values default to the initial state and medium priority. A synthetic import run identified deterministically from the archive content is reused when the same archive is imported again, so re-import is idempotent and reports zero changes. The report lists counts of created, updated and skipped topics and a list of per-topic errors; a failing topic does not stop the others. A malformed topic markup becomes a per-topic error entry rather than aborting the archive. _(bcf-beh-010; observed)_
- The strict 3.x reader refuses hostile archives before reading content: total archive size over its cap, more entries than its cap, an uncompressed total above its cap or any entry whose path is absolute, carries a drive letter or contains a parent-directory component aborts the whole parse as a security error (answered as request too large). A non-zip body, missing version marker, missing or non-3 version are format errors (answered as unprocessable). XML is parsed with entity expansion and external entities disabled. Optional project and extension documents that are malformed are ignored. Required topic fields are title, creation date, creation author, type and status; a topic missing any is returned with a parse error naming the missing fields and does not poison its neighbours. _(bcf-beh-011; observed)_
- Punch items exchange through BCF: export writes one topic per item in version 2.1 or 3.0 (selection optional; a selection matching nothing is refused) with the item's identifier as the topic GUID, a punch label plus category and trade labels, status and priority mapped to BCF words, the assignee and due date, a bounded number of photos (illustratively ten) each as a viewpoint with its image and, when the photo has an evidence record, a comment carrying one readable evidence line; viewpoint and comment identifiers are derived stably from the item and photo so repeated round trips never duplicate them. Import matches a topic to an item of the project by GUID (an item of another project is not touched and the topic becomes a new item with a warning; a non-UUID GUID yields a new identifier with a warning), can be restricted to topics carrying the punch label, applies title, description, priority, assignee and due date, applies status only for open, assigned, in progress and resolved (verified or closed produce a warning and no change), stores new snapshots as photos only when they are real images (otherwise warning), and records new comments in the item's metadata without duplicating known ones. The import report gives counts of created, updated, photos added, comments added, skipped, the item identifiers and findings. _(bcf-beh-012; observed)_
- A live REST profile of the open BCF API 3.0 standard offers: list and read projects, project extensions (topic types, statuses, priorities, stages and allowed actions), list/create/read/update/delete topics, list/create comments (with an optional reply-to reference to a parent comment of the same topic), list/create viewpoints and read a viewpoint snapshot, and read the current user. Topic reads return an entity tag derived from the last-modified instant; update and delete honour a conditional header and answer precondition-failed on mismatch; mutations are marked uncacheable. Topic listing supports the OData options $filter, $orderby, $top (a bounded page size with a default, illustratively default 50 and maximum 500) and $skip with a total count header. $filter supports comparisons (eq, ne, lt, le, gt, ge) on known scalar fields, membership (in), and a label-contains form, joined only by and; or, grouping and unknown fields are refused with a client error, as are over-long filters. Viewpoint creation is JSON (not XML), a duplicate viewpoint GUID is a conflict, snapshot data must be valid base64 PNG. GUID path segments must be canonical UUIDs (unprocessable otherwise). Each topic and comment reports the actions the caller's role may perform, by illustrative role tier: read-only roles get none; a limited-contributor tier may add comments and viewpoints; full contributor tiers and above may also update. The destination maps these tiers to its own role model. _(bcf-beh-013; observed)_
- Interface behavior: an issue counts as done when its status reads closed (case-insensitive substring); an open issue is overdue when its due date is earlier than now, with date-only due dates pinned to UTC midnight so local time zone does not shift the result. Status badge semantics are derived from keywords (closed neutral; resolved, done or approved positive; progress or review caution; open, new, active or reopen informational; anything else neutral) and priority badge semantics from keywords (critical, high or major strongly negative; normal, medium or minor caution). Editable statuses offer a common set plus the topic's current value so imported custom statuses survive an edit. A topic's primary viewpoint is the first with a snapshot, else the first, else none. The review dashboard rolls up total, open, closed, overdue, open-and-unassigned, counts by raw status, by raw priority and by assignee (busiest first, unassigned included), and ageing buckets of open issues by creation date (illustratively up to a week, up to a month, up to a quarter, and older). Thumbnails distinguish three empty states: failed to load, viewpoint without image, and issue without any viewpoint; only the first is shown as a failure. _(bcf-beh-014; observed)_

## Inputs

- Inputs: a BCF archive (2.1 or 3.0) uploaded as a file, an optional forced version, topic and comment and viewpoint payloads, an optional selection list of topic identifiers for export, optional status and severity filters for clash export, and query options for the live REST profile. _(bcf-in-001; observed)_

## Outputs

- Outputs: downloadable BCF archives; the register import report (status, detected version, four counters, findings); the clash import report (created, updated, skipped, per-topic errors with topic identifier and message); the punch import report; topic, comment and viewpoint records in the application's shape and in the standard's shape; snapshot images. _(bcf-out-001; observed)_

## States and transitions

- Topic status is free text; the application suggests common values and does not restrict transitions in the register. Mapped status words apply only in the clash and punch paths. _(bcf-st-001; observed)_

## Timing and ordering

- Register list is newest first and bounded by a hard cap per page with offset and limit paging; comments on the live profile are oldest first; export order of topics is the register order; archive building runs off the request path so other requests keep being served. Exporting the same data twice yields the same archive content for the 3.0 writer (stable element order, UTC timestamps). _(bcf-time-001; observed)_

## Edge cases

- Duplicate topic GUIDs within one export are rejected by the 3.0 writer as a programming error; the clash export guards against it by de-duplicating by signature first. _(bcf-edge-001; observed)_
- A viewpoint whose referenced viewpoint document is missing is still imported as a reference without camera data in the strict reader, and with a warning in the register import. _(bcf-edge-002; observed)_
- An issue raised outside a viewer or from a clash result may legitimately have no viewpoint or no image; neither is treated as a failure. _(bcf-edge-003; observed)_
- Information the application does not model (for example document references and BIM snippets in the standard's richer model) is not guaranteed to survive an import followed by an export; unmodelled data may be kept only as opaque extension data, and the live profile keeps a BIM snippet as opaque metadata. _(bcf-edge-004; inferred)_

## Errors

- Result classes: unsupported version, GUID or filter syntax problems, selection matching nothing: unprocessable/validation; empty or unreadable upload: client error; oversize: request too large; hostile archive in the strict reader: request too large; not a BCF archive in the strict reader: unprocessable; clash storage not available: service unavailable; unknown topic, comment, snapshot or project: not found (project access denial is indistinguishable from absence); precondition mismatch on the live profile: precondition failed; duplicate viewpoint on the live profile: conflict. _(bcf-err-001; observed)_

## What it must not do

- Content problems in an archive never produce a server error; hostile paths never write outside the archive model; BCF import into punch items never verifies or closes an item; clash import never overwrites assignee or due date of an existing issue. _(bcf-neg-001; observed)_

## Security

- Every operation requires a capability (read, create, update, delete, export or import) and access to the project; access failure is reported as not found. The live profile restricts visible projects to those the caller owns (administrators see all), which is narrower than the file-based paths that also admit team members. Archive reading is hardened against zip bombs, zip-slip and XML external entities. Topic folder names come only from validated GUIDs, never from user text. _(bcf-sec-001; observed)_

## Invariants

- Importing an archive produced by the application's own exporter into the same project leaves topics, comments and viewpoints unchanged in count and content for the modelled fields. _(bcf-inv-001; derived)_
- Identity across tools is the BCF GUID for register topics, the signature for clash topics and the item identifier for punch topics. _(bcf-inv-002; observed)_

## Notes

- The BCF formats (2.1 and 3.0) and the BCF API 3.0 profile are public open standards and the exact element and operation names of those standards must be kept for interoperability; application-specific mapping tables, report shapes, status vocabularies and numeric limits are behavior, not standard, and the destination may choose its own. _(bcf-comp-001; observed)_

## Non-goals

- Demo seed data for the register is out of scope.
- The clash detection engine itself is out of scope.
- Viewpoint capture inside the 3D viewer is only named, not specified.
- Localized message catalogues are not reproduced.
- Do not reproduce origin provenance markers.

## Test cases

- **bcf-test-001**: Given a project with two topics (one with two comments and a viewpoint with an image), when the register is exported as 3.0 and then imported into an empty project, then the topics, comments and viewpoints exist.  
  Expected: Report status passed with 2 topics, 2 comments, 1 viewpoint created; the image is attached; GUIDs preserved.
- **bcf-test-002**: Given the same archive imported a second time into the same project, then no duplicates appear.  
  Expected: Topics are reported as updated, counts of created comments and viewpoints are zero for already known GUIDs.
- **bcf-test-003**: Given an export request for version 2.5, then it is refused; given version 2.1, markup places comments beside the topic; given 3.0, inside it.  
  Expected: Validation error listing supported versions for 2.5; layout differences as described.
- **bcf-test-004**: Given a selective export naming three topic GUIDs of which two exist, then two topics are written; given a selection of only unknown GUIDs, then it is refused.  
  Expected: Archive has two topics and a count header of two; second request yields a validation error.
- **bcf-test-005**: Given a body that is not a zip, then import returns a report with errors and imports nothing; given an empty upload, a client error.  
  Expected: Report status errors with an archive-invalid finding; empty upload gives client error.
- **bcf-test-006**: Given an archive with three topics of which one has malformed markup, when imported through the register path, then nothing is written under the baseline all-or-nothing rule (subject to the corresponding decision point).  
  Expected: Report status errors listing the bad topic; counters zero.
- **bcf-test-007**: Given an archive whose version marker is absent, then import proceeds as 2.1 with a warning; given version 4.0 an error.  
  Expected: Status warnings and topics imported for the first; errors and no import for the second.
- **bcf-test-008**: Given an archive containing an entry with a parent-directory path component, when read by the register import, then that entry is skipped with a warning; when read by the strict 3.x reader the whole archive is rejected.  
  Expected: Warning finding for register import; request-too-large result for the strict reader.
- **bcf-test-009**: Given a viewpoint with 5 visible and 2 hidden components exported by the 3.0 clash writer, then the 2 hidden are written as exceptions with default visible; reading them back yields the same hidden list.  
  Expected: Exceptions block holds the shorter list and the default flag matches; read-back recovers the lists.
- **bcf-test-010**: Given clash results where two rows share a signature from different runs, one critical open and one resolved, when exported with status open, then one topic per signature appears using the newest row.  
  Expected: Topic type clash, GUID equal to the signature, priority from severity, labels clash type and severity, viewpoint synthesized when centroid non-zero.
- **bcf-test-011**: Given the clash archive imported twice into a project that already holds the issues, then the second run changes nothing.  
  Expected: First run reports updates for changed status, priority or tags; second run reports all skipped and zero created.
- **bcf-test-012**: Given an archive from another tool whose topic carries priority Major and status Closed and a non-signature GUID, when imported as clashes, then a new issue is created with priority high and status resolved.  
  Expected: Created count one; mapped values as stated; signature derived from the GUID by hashing.
- **bcf-test-013**: Given a punch item with two photos exported and re-imported after the topic status was changed to resolved in another tool and a comment added, then the item becomes resolved, gains the comment once, and no photo is duplicated.  
  Expected: Updated one, photos added zero, comments added one; second import adds nothing.
- **bcf-test-014**: Given a punch topic whose GUID belongs to an item of another project and another with a non-UUID GUID, when imported, then both become new items with warnings.  
  Expected: Created two; findings foreign-item and new-id; the other project's item untouched.
- **bcf-test-015**: Given the live profile, when a topic is fetched, updated with its tag, then updated again with the old tag, then the second update is refused.  
  Expected: First update succeeds and returns a new tag; second returns precondition failed.
- **bcf-test-016**: Given the live profile listing with a filter combining status equals Open and a label match, and then with an or-joined filter, then the first filters and the second is refused.  
  Expected: First returns matching topics with a total count header; second returns a client error.
- **bcf-test-017**: Given a read-only-role caller on the live profile, then topics report no permitted actions; given a limited-contributor caller, only comment and viewpoint creation.  
  Expected: Action lists as stated.
- **bcf-test-018**: Given open topics created 3, 20, 60 and 120 days ago, two with past due dates and one unassigned, and one closed topic, then the dashboard roll-up reports four open, one closed, two overdue, one unassigned and one in each ageing bucket.  
  Expected: Counts as stated; closed topic excluded from ageing and overdue.
- **bcf-test-019**: Given a comment that names a viewpoint not on its topic, then creation is refused; given a topic reference using the BCF GUID rather than the internal identifier, then the operation resolves; given a GUID from another project, not found.  
  Expected: Refusal, success, not found respectively.

## Open questions (decisions for QC Manager)

- Decision point: the register import abandons the whole archive when any topic has an error-level finding, while the clash import is resilient per topic. Should the destination import good topics and report bad ones, or keep all-or-nothing?
- Decision point: the register export defaults to BCF 2.1 whereas the clash export is BCF 3.0 only and the strict reader accepts only 3.x. Decide which versions the destination supports in each direction and which is the default.
- Decision point: the live BCF API profile shows only projects the caller owns, while the file-based paths admit team members. Which visibility rule should the destination apply?
- Decision point: an entity tag derived solely from the last-modified instant can collide when two different edits carry an identical instant. Decide on the concurrency token (a version counter is an alternative).
- Decision point: there are two separate codecs (a dual-version codec for the register and punch items, and a 3.0 writer/reader pair for clashes) with overlapping behavior and slightly different tolerance (for example in label and comment placement). The destination may unify them if the observable behavior listed here is preserved.
- Decision point: status vocabularies differ per path (open, in progress, resolved, closed in the register; clash states; punch states). A neutral mapping table is a product decision.
- Decision point: size and count limits are inconsistent between the register path, the strict reader and the upload cap. The destination should state one coherent set of limits.
- Decision point: whether exported archives should carry any application-level export metadata is a separate product decision for the destination.
- Unknown: full behavior of the viewpoint capture hook, the coordination-meeting mode and the printable report was only named, not traced, and is not specified here.
- Unknown: how unmodelled standard fields (document references, snippets, related topics) behave on a full round trip.
