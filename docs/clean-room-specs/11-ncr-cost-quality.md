# 11. NCR cost, cost of quality, back-charges

Spec `spec-ncr-cost-quality-001` · compatibility: behavior-compatible · leakage review: passed

## Summary

Cost money flows from quality records into commercial recovery and quality reporting. An NCR carries a free-text cost impact; a punch item carries a priced rework cost with its own currency; a back-charge record can be raised from an NCR or a punch item, linked to a subcontractor or contact, prefilled from the source record, split across responsible parties, tracked through an agree/recover/waive lifecycle, rolled up per party and per currency, listed as pending deductions per subcontractor, and analysed as a recovery rate by evidence-strength cohort. Quality reporting computes cost of poor quality as NCR cost plus recorded rework cost of still-open punch items, converting only where an exchange rate exists and never inventing amounts. Subcontract linkage lives on the back-charge, not on the NCR itself. All numeric bounds, tolerances and limits in this spec are illustrative parameters; the destination chooses its own values.

## Behaviour

- An NCR stores its cost impact as short free text with a bounded length (illustratively a few dozen characters) in which an amount and an optional currency code are written together, with the code before or after the number. A non-zero cost impact requires a non-empty description; this is a blocking rule on create and update. A closed NCR must record root cause and corrective action (blocking) and should name its verifier (warning only). An NCR still open past its due date is flagged as overdue (warning only). _(ncq-beh-001; observed)_
- An NCR can be linked to a change order of the same project. The link is checked on create and whenever it changes: a value that is not a valid identifier, a change-order capability that is disabled or absent, or an order that does not exist in the NCR's project is refused with a client error. An unchanged legacy value is not re-checked on unrelated edits. _(ncq-beh-002; observed)_
- A closed or void NCR cannot be edited. A closed or void NCR cannot be deleted (conflict result), because it is kept as the quality record; voiding is the way to remove an NCR raised in error from the open register. _(ncq-beh-003; observed)_
- Closing an NCR that has a cost impact publishes, after the transaction commits, a notification so that other capabilities can react: a variation can be drafted automatically and a change-review candidate can be raised. Closing an NCR without cost impact publishes nothing of this kind. Creating an NCR notifies the project owner with the NCR number, title and severity. _(ncq-beh-004; observed)_
- Raising a variation from an NCR on demand requires a non-empty cost impact (client error otherwise) and is refused with a conflict for a void NCR (a void NCR has no cost to recover); a closed NCR is allowed. The operation is idempotent per NCR: if the NCR already points at an existing change order, that order is returned unchanged instead of creating another; if the earlier order was deleted a new one is created. Concurrent invocations are serialized per NCR, together with any automatic drafting path, so two orders can never be created for one NCR. _(ncq-beh-005; observed)_
- When a variation is raised from an NCR, the amount and currency are read out of the free-text cost impact using the decimal convention the author typed (for example a text with a comma as decimal separator and dot as thousands separator reads as the full thousands amount, not a small one), accepting a currency code before or after the amount. A single separator followed by exactly three digits is settled using the project currency as a hint. If no single non-negative amount can be read, the order is created with amount zero and flagged for human review as ambiguous or unreadable; a negative reading is treated as zero. The currency is the one written in the text, else the project's currency, else blank. _(ncq-beh-006; observed)_
- If a non-zero amount is read but neither the text nor the project names a currency, the variation is created at amount zero, flagged for review and marked as missing a currency, with the original text preserved. An amount of absurd magnitude is refused with a client error stating the cost is outside the supported range. The created order uses a non-conformance reason, a title prefixed as a variation from the NCR title (truncated), a description composed from NCR number and title, description, corrective action and root cause, a non-negative schedule impact in days, and metadata recording the source NCR, its number and the raw cost text. The order is then linked back to the NCR. _(ncq-beh-007; observed)_
- A punch item has an optional rework cost kept as a decimal in text form with its own currency. An empty value means not priced, which is different from zero. When a new item is created without naming a currency, it takes the project's currency if that is a valid three-letter alphabetic code (upper-cased), else a configurable default currency; a currency explicitly supplied by the caller is always kept, even when it equals the default currency. Lookup failures degrade to the default and are logged. _(ncq-beh-008; observed)_
- In the interface, a typed rework cost accepts several number grammars (thousands separator with dot and decimal comma, thousands separator with comma and decimal dot, leading currency sign), refuses negative or unreadable input, treats empty input as not priced, keeps the normalized text rather than a float re-serialization to avoid precision loss, shows legacy exponent-form values as plain numbers, and displays a priced item in its own recorded currency. The currency offered is the project's. _(ncq-beh-009; observed)_
- A back-charge records a cost the project intends to recover from a responsible party. Fields: free-text responsible party, description, basis, gross amount, chargeable percentage as a fraction from zero to one (default one, fully chargeable), currency, recovered amount, source reference, and a lifecycle state from proposed, agreed, disputed, recovered, waived (default proposed). Optional links: a subcontractor, a contact, an NCR, a punch item, and a change subject whose evidence strength is assessed by a separate capability and used for traceability. _(ncq-beh-010; observed)_
- Subcontract linkage: a back-charge naming a subcontractor that does not exist is refused (client error); a named contact that does not exist is refused. When only a subcontractor is given, the subcontractor's own contact is attached; when only a contact is given, a subcontractor pointing at that contact is attached if one exists. A blank responsible party is filled with the subcontractor's legal or trade name, else the contact's company, legal or personal name. Re-linking on update takes the new subcontractor's contact rather than keeping the old party's. _(ncq-beh-011; observed)_
- Back-charges raised from NCRs and punch items: a named NCR or punch item must exist in the same project, otherwise a client error and nothing is stored. From a punch item the back-charge prefills description (item title), gross amount (rework cost if readable as a non-negative plain decimal) and currency (rework currency). From an NCR it prefills the source reference (NCR number), description (when not already set by the punch item) and, when no gross was found yet, gross amount and currency parsed from the NCR cost-impact text (decimal with a point only; decimal comma, ranges and prose are not guessed at; negative values ignored). A value explicitly sent by the caller always wins over a prefill. Currency falls back to the source currency, then the project currency, then blank. _(ncq-beh-012; observed)_
- Money rules for a back-charge: chargeable amount equals gross times the chargeable fraction clamped into zero to one, rounded to two decimals half-up. Outstanding equals chargeable minus recovered, never below zero, and zero for recovered or waived items. Money never mixes currencies: every total is scoped to one currency. _(ncq-beh-013; observed)_
- Recovery ledger per project: rows per responsible party and currency (a party holding charges in two currencies yields two rows; blank party falls into an unassigned bucket) with item count, open count (items not yet recovered or waived), gross, chargeable, recovered (clamped to chargeable) and outstanding totals, ordered by descending outstanding then party then currency; rows per currency ordered by descending chargeable total; a headline currency chosen as the currency with the largest chargeable total (ties alphabetical) with its outstanding total; empty input gives an empty headline currency and zero. _(ncq-beh-014; observed)_
- Apportionment splits a back-charge's chargeable amount across responsible parties by fractional shares. Shares must be non-empty, non-negative and sum to one within a small tolerance (illustratively one ten-thousandth); duplicate parties are merged by summing, blank parties become unassigned. Each party amount is the chargeable amount times the share rounded half-up to two decimals, and the rounding residual is added to the largest share (first listed wins ties) so the amounts sum exactly to the chargeable amount. Re-apportioning replaces the earlier split. Invalid shares give a validation error; an unknown back-charge gives not-found. The stored split reports the share total and whether an apportionment exists. _(ncq-beh-015; observed)_
- Pending deductions for a subcontractor (optionally within one project): only back-charges in the agreed state count (proposed and disputed are not yet owed; recovered and waived are settled). The amount is the outstanding figure. For an apportioned charge only the shares naming this subcontractor (by identifier, legal name, trade name, or the charge's own responsible-party label) count, scaled by outstanding divided by chargeable; a charge apportioned wholly to others contributes nothing; zero amounts are omitted. Totals are per currency and never summed across currencies. Whoever applies a deduction must also move the recovered amount or the same money would be deducted again. _(ncq-beh-016; observed)_
- Recovery performance: recovery rate is recovered divided by chargeable as a fraction rounded to four decimals half-up, clamped between zero and one, and undefined (absent, never zero) when nothing was chargeable. Items are grouped per currency and by traceability: individual evidence-strength bands (illustratively strong, moderate, weak) and a two-way cohort split where high means the strongest band and low means all others; an item with a blank or unrecognized band counts as weak so an unscored charge never inflates the high cohort. Absorbed amount is the chargeable less anything recovered for items waived or absorbed, floored at zero, reported per cohort. The same computation is available for one project and as a pooled portfolio over the projects the caller may access (an administrator sees all; no accessible projects yields an empty result). _(ncq-beh-017; observed)_
- When a back-charge is linked to a change subject, that subject is assessed for how provable it is by a separate capability and the resulting band and score are stamped on the back-charge so the recovery analysis can place it in the right cohort; an unknown subject kind gives a client error and a subject not found in the project gives not-found; either failure rolls the whole creation back. Without a linked subject, no band is stamped and the item counts as weak. _(ncq-beh-018; observed)_
- Cost of poor quality in quality reporting equals the total of NCR cost amounts (cancelled NCRs excluded) plus the rework term. NCR amounts held in a foreign currency are converted into the project base currency using the project's own exchange-rate list (units of base per unit of foreign); a currency with no usable rate is added at face value rather than dropped, so a missing rate degrades visibly. The report currency is the explicit request, else the project currency, else empty (reported as unknown, never replaced by a guessed currency). _(ncq-beh-019; observed)_
- The rework term is the sum of recorded rework cost of punch items that are not yet verified or closed, counted only where the item's own currency equals the report currency; punch money is never converted. Items with no cost count as unpriced (not zero), items with unreadable or non-finite cost count as unreadable and never break the report, items with a blank currency fall into an unstated bucket. The report returns the per-currency map, priced, unpriced and unreadable counts, a mixed-currency flag and a basis label that distinguishes: no open punch items, none priced, currency unknown, currency mismatch (cost exists but in other currencies), recorded, source unavailable, and caller override. If the caller supplies a per-item rate the term is that rate times the open punch count used by quality reporting, taken verbatim, and a rate of zero is honoured. _(ncq-beh-020; observed)_
- A detailed variant of the cost of poor quality adds caller-supplied warranty cost and delay-penalty cost (both default zero) to the NCR and rework terms, and returns the same explanatory fields (basis, counts, currency map). The quality management review report includes the cost of poor quality total, the open punch count and the rework basis. _(ncq-beh-021; observed)_
- On the NCR screen, for an NCR with a positive cost impact, the user is offered an action to raise a variation and a control to raise a back-charge from that NCR; cost impact is shown compactly in the list only when positive and otherwise as an empty marker. Closing is disabled until a corrective action exists, with a hint saying so. _(ncq-beh-022; observed)_
- NCR statuses are six: identified, under review, corrective action, verification, closed, void. Closed and void are terminal; every other status is non-terminal. Requirement: one consistent definition of open applies everywhere an open figure is produced (register summary counters, insight measures, overdue evaluation, and any report): an NCR is open exactly when it is in a non-terminal status. A register summary must reconcile, meaning every NCR is counted in exactly one status group or the grouping is explicitly per status, so that group counts add up to the total; no NCR in active corrective work may be reported as not open. Interface lifecycle helpers treat closed and void as terminal. _(ncq-beh-023; derived)_

## Inputs

- Back-charge create input: optional responsible party, description, basis, gross amount, chargeable fraction, currency, status, source reference, subcontractor, contact, NCR reference, punch item reference, optional change subject kind and identifier. Update input: any subset of amounts, party, status, recovered amount and party links. _(ncq-in-001; observed)_
- Apportionment input: a list of parties each with a fractional share and an optional basis text; the first non-empty basis for a party is kept. _(ncq-in-002; observed)_
- Cost of poor quality input: project, optional report currency, optional per-item rework rate, and for the detailed variant optional warranty and delay amounts. _(ncq-in-003; observed)_

## Outputs

- A back-charge is returned with money as exact decimal strings: gross, chargeable fraction, derived chargeable amount, recovered and outstanding amounts, an open flag, agreed and recovered times, traceability band, link identifiers and any non-blocking validation warnings. _(ncq-out-001; observed)_
- Pending deductions are returned with the subcontractor, a list of items (back-charge reference, project, source reference, description, currency, amount, apportioned flag) and per-currency totals as decimal strings. Recovery performance returns per currency the item count, chargeable, recovered, outstanding and absorbed totals and rate (or absent), plus cohort and band breakdowns, and a headline currency and rate. _(ncq-out-002; observed)_

## States and transitions

- Back-charge lifecycle: proposed may go to agreed, disputed or waived; agreed may go to recovered, disputed or waived; disputed may go to agreed or waived; recovered and waived are final. A recovery is only booked against an agreed claim. The agreed time is stamped the first time the item becomes agreed and the recovered time the first time it becomes recovered. _(ncq-st-001; observed)_
- NCR lifecycle: identified to under review or void; under review to corrective action, back to identified, or void; corrective action to verification, back to under review, or void; verification to closed or back to corrective action; closed and void are final. Closing by explicit close action requires the verification state and a recorded corrective action; closing by a status edit records the acting user as verifier when none is recorded. _(ncq-st-002; observed)_

## Timing and ordering

- Cross-capability notifications about an NCR close or a back-charge being recorded are deferred until after the originating transaction commits, so subscribers reading the data in their own sessions see the committed state. The back-charge recorded notification feeds the project timeline. _(ncq-time-001; observed)_
- Back-charge list is oldest first; ledger and analytics ordering is as stated in the behavior claims. _(ncq-time-002; observed)_

## Edge cases

- A row whose chargeable fraction was never set is treated as fully chargeable when read, not as zero, so the ledger is not understated. _(ncq-edge-001; observed)_
- Over-recovery never drives outstanding negative nor lifts recovered above chargeable in any rollup; a recovered amount above the chargeable amount beyond a small tolerance is a validation error on write. _(ncq-edge-002; observed)_
- A back-charge may be created with gross amount omitted and no source to prefill from; gross then defaults to zero and the currency may be blank. When money is present a currency must be stated and every apportionment row must carry the same currency. _(ncq-edge-003; observed)_
- Cost of poor quality with no open punch items, with open items none of which is priced, or with priced items only in another currency produces a rework term of zero together with a basis label that says which of these cases applies, so the reader can tell an unrecorded cost from a measured zero. _(ncq-edge-004; observed)_
- A punch item reaches the cost-of-quality rework term only while it is not verified or closed; once verified its rework money drops out of the figure. _(ncq-edge-005; observed)_

## Errors

- Back-charge create or update: unknown subcontractor, contact, NCR or punch item (or one from another project) gives a client error and rolls back; unknown change subject kind gives a client error; change subject not in project gives not-found; unknown back-charge on update or apportion gives not-found; invalid shares give a validation error; a status value outside the five allowed is a validation error that lists accepted values; blocking money-rule violations are refused with a coded validation error while warning-level findings are attached to the response. _(ncq-err-001; derived)_
- Variation from an NCR: no cost impact gives client error; void NCR gives conflict; out-of-range amount gives client error; change orders unavailable or failing their own rules produce the coded errors of that capability. _(ncq-err-002; observed)_
- Raising an NCR that carries a typed positive cost amount without a currency is refused, because accepting it silently would make the cost-of-poor-quality total meaningless. _(ncq-err-003; observed)_

## What it must not do

- No money figure in the cost of poor quality is ever a built-in constant; every term comes from recorded amounts or caller input, and an unpriced item is never counted as zero cost. Amounts in different currencies are never added together in ledgers, pending deductions, performance or rework (NCR conversion with a project-supplied rate is the only conversion, and a missing rate falls back to face value). _(ncq-neg-001; observed)_
- Nothing on the NCR record itself carries a subcontractor reference or a back-charge amount; subcontract and back-charge linkage is held on the back-charge side only. _(ncq-neg-002; observed)_

## Security

- Every back-charge operation is scoped to a project the caller can access; a project that does not exist and one the caller cannot see give the same not-found result so existence is not leaked. Reading requires a read capability and writing (create, update, apportion) a write capability. The portfolio view is limited to the caller's accessible projects. A back-charge may only reference NCRs and punch items of its own project. Raising a variation from an NCR checks project access so an edit-capable user cannot escalate an NCR of a project they cannot see. _(ncq-sec-001; observed)_

## Invariants

- Apportioned party amounts for one back-charge always sum exactly to its chargeable amount. _(ncq-inv-001; observed)_
- Per currency, outstanding total never exceeds chargeable total and recovered total never exceeds chargeable total. _(ncq-inv-002; derived)_
- One NCR yields at most one linked change order through the on-demand raise action, however many times it is invoked. _(ncq-inv-003; observed)_
- All money is held and exchanged as exact decimals (strings on the wire), never binary floating point; rounding is half-up to two decimals for amounts and four for rates. _(ncq-inv-004; observed)_

## Notes

- Equal-output expectation: money fields are decimal strings; rates are fractions not percentages; the five back-charge states, the share-sum tolerance for apportionment and the basis categories of the rework term are the observable vocabulary clients depend on; ledger and pending-deduction ordering as specified. Numeric tolerances, length bounds and default currency are illustrative parameters that the destination may set. _(ncq-comp-001; observed)_

## Non-goals

- Photo, location and BCF aspects of punch items are out of scope.
- The scoring method for change-subject provability is not described here.
- Tax, retention and payment mechanics of deductions are not described.
- No storage layout or code structure is specified.
- Do not reproduce origin provenance markers.

## Test cases

- **ncq-test-001**: Given an NCR with cost impact text of the form three-letter code then 8400 and a project in another currency, when a variation is raised from it, then the order uses the written code and amount 8400.  
  Expected: A change order is created with amount 8400 in the written currency, reason non-conformance, linked back to the NCR.
- **ncq-test-002**: Given an NCR already linked to a change order, when the raise action is invoked again, then no second order is created.  
  Expected: The existing order is returned unchanged.
- **ncq-test-003**: Given a void NCR with a cost impact, when a variation is requested, then it is refused; and given an NCR with no cost impact the request is refused as a client error.  
  Expected: Conflict for void; client error for missing cost.
- **ncq-test-004**: Given an NCR whose cost text has digits but cannot be read as one clear amount, when a variation is raised, then it is created at zero and flagged for review with the original text kept.  
  Expected: Order amount zero, review flag set, raw text preserved.
- **ncq-test-005**: Given an NCR with a non-zero cost impact but an empty description, when it is created or edited, then it is refused with a coded validation error.  
  Expected: Validation error; nothing stored.
- **ncq-test-006**: Given a project whose currency is a euro-style code, when a punch item is created without naming a currency, then the item takes the project code; when another item explicitly names the default currency it keeps it.  
  Expected: First item priced in project currency; second keeps its explicit currency.
- **ncq-test-007**: Given the typed inputs 1.250,50 and 1,250.50 and a text with a leading currency sign before 1250, plus a negative value and an empty value, when the rework cost field is read, then positive forms are accepted, the negative is refused and empty means not priced.  
  Expected: Two equal accepted values, one accepted with the sign stripped, one refusal, one not-priced result.
- **ncq-test-008**: Given a punch item with a priced rework cost of 600.00 in the project currency and an NCR with cost impact text 5000.00, when a back-charge is created naming both and sending no gross, then the gross comes from the punch item and the reference and fallback description from the NCR.  
  Expected: Gross 600.00, currency from the punch item, source reference equal to the NCR number, description equal to the punch item title.
- **ncq-test-009**: Given a back-charge naming a subcontractor and no responsible party, when it is created, then the party label and contact come from the subcontractor.  
  Expected: Responsible party equals the subcontractor's legal or trade name; contact attached.
- **ncq-test-010**: Given a back-charge naming an NCR of another project, when it is created, then it is refused.  
  Expected: Client error that the NCR is not found in this project; no record created.
- **ncq-test-011**: Given gross 1000.00, fraction 0.6 and recovered 200.00 in one currency, when the item is read, then chargeable is 600.00 and outstanding 400.00; when marked recovered, outstanding becomes 0.00.  
  Expected: Amounts as stated.
- **ncq-test-012**: Given a chargeable amount 100.00 and shares 0.333, 0.333 and 0.334 for three parties, when apportioned, then amounts sum to 100.00 with any cent residual on the largest share; with shares summing to 0.9 the request is refused.  
  Expected: Amounts 33.30, 33.30, 33.40 summing to 100.00; second request gives a validation error.
- **ncq-test-013**: Given charges for one party in two currencies and one charge with blank party, when the ledger is built, then two rows exist for the first party and an unassigned row for the blank; the headline currency is the one with the larger chargeable total.  
  Expected: Rows separated by currency, unassigned bucket present, headline chosen as stated, no cross-currency sum.
- **ncq-test-014**: Given a subcontractor with one agreed charge of outstanding 300.00, one proposed charge, and one agreed charge apportioned half to another party, when pending deductions are requested, then only the agreed amounts count and the apportioned charge contributes the subcontractor's share.  
  Expected: Items list the agreed full charge and half of the apportioned one; proposed excluded; totals per currency.
- **ncq-test-015**: Given an agreed charge, when it is moved to disputed and later waived, then each move is accepted; when a recovered charge is moved back to agreed, it is refused.  
  Expected: Waived becomes final; recovered cannot go back.
- **ncq-test-016**: Given recovered 450.00 of chargeable 500.00 in the strongest-evidence cohort and nothing recovered of 500.00 waived in the weak cohort, when performance is computed, then the high cohort rate is 0.9000, the low cohort rate 0.0000 with 500.00 absorbed, and a currency with zero chargeable shows no rate.  
  Expected: Rates and absorbed amounts as stated; absent rather than zero for zero chargeable.
- **ncq-test-017**: Given a project with base currency X, NCR costs of 1000 in X and 100 in Y with a rate of 1.1 for Y, and 2 open punch items priced 300 and 200 in X plus one priced 50 in Y, when cost of poor quality is computed, then NCR total is 1110, rework is 500 and total 1610, with the basis recorded and the mixed-currency flag on.  
  Expected: Totals as stated; the Y punch money is reported in the per-currency map but excluded from the total.
- **ncq-test-018**: Given the same project, when Y has no rate, then the Y NCR cost is added at face value; when no open punch is priced the rework term is zero with a none-priced basis; when a per-item rate of zero is supplied it is used.  
  Expected: Face-value fallback; basis label distinguishes unpriced from zero; override of zero honoured.
- **ncq-test-019**: Given an NCR with a typed positive cost amount and no currency, when it is raised, then it is refused.  
  Expected: Validation error requiring a currency.
- **ncq-test-020**: Given a closed NCR, when a user tries to edit or delete it, then both are refused; when the same user voids an open NCR it leaves the open register.  
  Expected: Edit refused with client error, delete refused with conflict; void is accepted.
- **ncq-test-021**: Given a register with one NCR each in identified, under review, corrective action, verification, closed and void, when the register summary counters, the insight open measure and the overdue evaluation are read.  
  Expected: Total is 6; open is 4 in every reader (the four non-terminal statuses); closed is 1; void is reported distinctly or excluded by an explicit documented rule; summary groups reconcile to the total.

## Open questions (decisions for QC Manager)

- Decision point: define one open set for NCRs and use it for every counter, insight measure and overdue evaluation. The four non-terminal statuses (identified, under review, corrective action, verification) are the proposed set. Decide also whether the register summary shows an open figure as that set or one counter per status, and where void NCRs appear besides the total.
- Decision point: the NCR cost impact is free text with a bounded length, which forces amount-and-currency parsing in several places (variation, back-charge prefill) with different strictness (one reader accepts decimal commas and flags ambiguity, another accepts only plain dot decimals). Should the destination store a typed amount and currency on the NCR instead, and if the application already has such fields, which behaviors should be preserved at the read boundary?
- Decision point: if the destination has more than one NCR record concept (for example a general register and a quality-management record with typed cost and currency), decide which record feeds the cost of poor quality figure.
- Decision point: an NCR does not itself link to a subcontractor; the link is on the back-charge. Should the destination add a responsible-party link to the NCR, or keep linkage on the back-charge only?
- Decision point: a variation can be created both on demand and automatically on NCR close with a cost impact, serialized per NCR. Whether the destination wants both paths is a product choice.
- Decision point: the recovery-performance cohort cut (strongest evidence versus everything else) and the default of weak for unscored items are product choices that drive the headline contrast; confirm before adopting.
- Decision point: apportionment accepts a share sum within a small tolerance; confirm the tolerance and the rule that rounding residual goes to the largest share.
- Decision point: analytics refer to an absorbed outcome that the back-charge lifecycle itself does not offer (only waived); decide whether a distinct absorbed state is needed.
- Decision point: punch rework money is excluded from cost of poor quality when its currency differs from the report currency and is never converted, while NCR money is converted; confirm this asymmetry is wanted.
- Unknown: the exact blocking-versus-warning severity of each back-charge money rule and which rules also run on apportion and update paths.
- Unknown: internals of the by-band and by-cohort aggregation and any further cost-recovery breakdown were analysed only in part.
- Unknown: how other capabilities (change orders, change-of-scope, subcontractor ratings, dashboards) consume NCR and back-charge data; only the producing side was analysed.
