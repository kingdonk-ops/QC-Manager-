# 09. Cross-project inbox and alerts

Spec `spec-inbox-alerts-001` · compatibility: behavior-compatible · leakage review: passed

## Summary

Per-user notification store with read/unread state, deletion, retention cleanup, locale-aware text resolution and an icon category; routing preferences per event kind and channel (in-app, email, outbound webhook) with realtime, hourly and daily cadence and a periodic digest flush; fan-out sinks (live push to the user's open sessions, email, signed outbound webhooks with failure circuit-breaking); event-driven generation of notifications with recipient-selection rules; a combined cross-project triage inbox (pending approval steps of two kinds and unread alerts of the caller, scoped to projects the caller can access, newest first, with severity, filterable by kind, project and severity on the client, with acknowledge, dismiss and restore stored per user); and small per-user count badges for navigation entries. Generator groups beyond the first few were only partly inspected and are listed in open questions. All numeric defaults, caps, thresholds and intervals in this spec are illustrative; the destination chooses its own values.

## Behaviour

- A notification belongs to exactly one user. It carries a type label, optional related-record kind and id, a title text key, an optional body text key, a map of text parameters, an optional relative link target, a read flag with read timestamp, free-form metadata and creation/update timestamps. Titles and bodies are stored as keys plus parameters, not as finished sentences. _(inb-beh-001; observed)_
- Creating a notification for several recipients produces one independent notification per recipient, each with the same content. _(inb-beh-002; observed)_
- When a notification is stored, a best-effort internal announcement carrying the full renderable content (keys, parameters, link, related record) is published; a failure to publish never prevents or rolls back the notification. External chat connectors and the live push both consume this announcement. _(inb-beh-003; observed)_
- The list response returns the page of items, the total count under the active filter, and the user's overall unread count (unaffected by the filter). Items are ordered newest first. Each item additionally carries a rendered fallback title and body written in the reader's own interface language and date order (English when the reader's settings cannot be read), the parameters with display date adjusted for the reader, and an icon category derived from the notification type (unknown types map to the informational category). _(inb-beh-004; observed)_
- Icon categories available to clients form a small closed set: success, error, warning and informational, plus a few domain-specific categories. The destination defines its own set and mapping; only the rule that unknown types fall back to informational is required. _(inb-beh-005; observed)_
- Notifications stored under an older key convention (title and body key identical) are presented using the current title/body key pair: when a stored key has an exact alias in a small fixed mapping, the response exposes the canonical keys. Whether the destination needs such aliasing depends on whether it migrates older stored rows. _(inb-beh-006; observed)_
- Marking read is scoped to the calling user and to currently unread rows; marking all read stamps every unread row of the caller and reports how many changed. Announcements are published only when something actually changed. _(inb-beh-007; observed)_
- Deleting is scoped to the owner. Notifications older than a configurable retention window (illustratively on the order of a few months, by creation time) are removed by a daily cleanup regardless of read state. _(inb-beh-008; observed)_
- Routing a prospective notification for a user: a no-delivery channel value is always suppressed; a stored preference for (user, event kind, channel) that is disabled suppresses; no stored preference or realtime cadence delivers immediately; hourly or daily cadence queues the payload for a later digest. The outcome is reported as delivered, queued or suppressed. _(inb-beh-009; observed)_
- Immediate delivery on the in-app channel stores a notification (taking title/body keys, type label, related record, link, metadata from the payload, with defaults derived from the event kind when absent). Immediate delivery on any other channel hands the payload to the email or webhook sink via an internal announcement, or defers it to a caller-supplied outbox so that nothing is sent for work that is later rolled back. _(inb-beh-010; observed)_
- A digest flush for one channel gathers all unsent queued items whose scheduled time has arrived, groups them by user, and produces one combined notification per user (an in-app summary notification with a count, or a combined email/webhook payload listing each item), then stamps every contributing item as sent. It returns the number of queued items sent, not the number of digests. Items are claimed before sending so two simultaneous flushes never send the same item twice. _(inb-beh-011; observed)_
- A background worker started with the application flushes the in-app, email and webhook digest queues on a short fixed interval (illustratively a few minutes) and performs retention cleanup and other periodic maintenance on a daily cycle. The first run happens after the first interval. A failing iteration never stops the schedule; transient database unavailability retries sooner using an exponentially growing delay capped at the normal interval, logged once per failure streak. _(inb-beh-012; observed)_
- Email delivery resolves the recipient's address, name, language and date order at send time; a recipient who no longer exists, is deactivated or erased receives no email but keeps in-app notifications. Messages are written in the recipient's language, the subject is prefixed with the project name when the parameters name one, links are made absolute against the public frontend address, and a daily per-recipient mail budget gates sending. A digest email lists each item as a bullet and uses a digest-specific subject with the item count. _(inb-beh-013; observed)_
- Webhook delivery posts a JSON envelope (unique id, event kind, user id, channel, payload, timestamp) to every active target whose comma-separated filter matches: a lone wildcard matches everything, a trailing namespace wildcard matches by dotted prefix, otherwise exact match; an empty filter matches nothing. If the target has a secret, the body is signed with a keyed SHA-256 digest sent in a signature header; each delivery also carries an event-kind header and the envelope id as an idempotency key. Each request has a short timeout (illustratively a few seconds). _(inb-beh-014; observed)_
- Webhook targets track last status code, last attempt time and consecutive failure count (success resets to zero; any non-2xx, refusal or exception increments). A target at or above a lower failure threshold is skipped; at or above a higher threshold it is automatically deactivated. The target address is re-validated after name resolution on every delivery and internal, loopback, private and cloud-metadata addresses are refused. One bad target never blocks the others. _(inb-beh-015; observed)_
- Live push: every open session of a user (multiple tabs) receives the same message when a notification is stored for that user. Sessions that fail to receive are silently dropped. After connecting, the first server message confirms the channel is live; a text keep-alive frame is answered; other frames (including binary) are ignored without closing the channel. Delivery is local to the process that holds the session. _(inb-beh-016; observed)_
- Notifications are generated by event handlers reacting to activity in other functional areas of the application (for example approval workflows, information requests, risk ownership, meeting follow-ups, service and billing work, subcontractor and supplier events, contract and commercial events, field and site events including sensor alerts, change and variation management, discussion comments, and deadline alerts). Each handler skips silently when the required recipient or record id is missing, runs in its own isolated transaction, and swallows all failures so the originating action is never affected. The destination chooses which of its own events generate notifications. _(inb-beh-017; observed)_
- Recipient selection rules: never notify the person who performed the action; each person once, in first-seen order; non-user placeholders (such as role labels held in an owner slot) are ignored; deactivated or removed accounts are dropped; for variation submissions and change-order approvals the named holder of the next action is told, and only when the record names no active holder at all do the project managers get told (a record whose holder is the actor tells nobody); decisions go to the originator. A change-order approver is not asked twice for the same submission step (initial manager notice and first approver count as one), but a resubmission after rejection asks again. _(inb-beh-018; observed)_
- Notifications for project discussion comments go to every distinct earlier commenter on the same record plus the project owner, minus the comment author, ordered deterministically and capped at a bounded recipient count. The link points to the project (or to a discussion overview when no project is known) and the preview is truncated to a bounded length. The destination chooses both bounds. _(inb-beh-019; observed)_
- Site sensor alerts (limit exceeded, device offline, strength reached) notify the active site managers and foremen of the project who have a user account, excluding the project owner; they are ignored when the device does not belong to the stated project. Numeric readings are formatted compactly. _(inb-beh-020; observed)_
- For variation and change-order notices, delivery honours each recipient's preferences on both in-app and email channels; realtime emails are released only after the in-app write has committed. Handlers verify the record's current status matches the announced transition before notifying, to avoid announcing a change that did not persist. A rejection reason is quoted up to a bounded length. _(inb-beh-021; observed)_
- A catalogue of known event kinds (module, short description) is exposed read-only to any signed-in user to drive the preferences screen. _(inb-beh-022; observed)_
- Combined inbox: one list of the caller's pending approvals (document-approval steps and change-request approval steps) and unread alerts across the projects the caller can access. Each row has a stable identifier that is unique per underlying record and encodes which kind of pending work it is, a kind (approval or alert), a source label, a title or title key with parameters, a body key (alerts), project id and name, related record type and id, a relative link, a severity (info, warning or critical), a creation time and an acknowledged flag; document-approval rows also carry the step's role label and alert rows carry the notification type label. The response also gives a scoped total, approvals count and alerts count (all computed after visibility scoping and after removing dismissed rows, before the final row cap) and a generation time. The row cap is selectable within a bounded range with a modest default; the compact widget uses a small cap and the full page a larger one (all illustrative). _(inb-beh-023; observed)_
- Kinds of pending work collected: (1) document-approval steps assigned to the caller whose own decision is still pending, where the parent approval workflow is still under review and belongs to a project the caller can access; (2) change-request approval steps assigned to the caller whose decision is still pending, where the parent change request has not reached a final status and belongs to an accessible project; (3) the caller's own unread in-app notifications, shown as alerts. Whether a step qualifies only when it is the caller's turn in a multi-step chain is a destination decision (see open questions). _(inb-beh-033; observed)_
- Row content per kind. Document-approval rows: warning severity; creation time is the workflow's submission time; the fallback title names the document kind; a translation key plus a body parameter holding the document kind (a generic word when absent); the link targets the screen where document approvals are handled; related record is the workflow. Change-request rows: warning severity; no creation time; the fallback title includes the change request's code when present; parameters hold code and title (empty text when absent); the link targets the change-request screen highlighting that request; related record is the change request. Alert rows: title and title key are both the notification's title key; body key and parameters come from the notification (empty map when absent); link and related record come from the notification; creation time is the notification's. _(inb-beh-034; observed)_
- Project association and visibility filtering: approval rows always carry the project of their parent record. An alert is tied to a project when its related record is itself a project, otherwise when its parameter map carries a project identifier; otherwise it has no project. After collection, a row whose project is set and not among the caller's accessible projects is silently dropped (never an error); rows with no project are always kept (they are the caller's own). Project names are filled from the caller's accessible project list. _(inb-beh-035; observed)_
- Accessible projects: for a non-administrator, non-archived projects the caller owns or is a team member of; for an administrator, all non-archived projects. An optional organisation-level scope may narrow the list further; whether it applies to everyone including administrators is a destination decision. The approval collectors are skipped entirely when the list is empty (alerts are still collected). How alerts naming projects outside the list are treated for administrators is a decision point (see open questions). _(inb-beh-036; observed)_
- Disabled or failing contributing features: each of the three streams is read independently; if a stream's feature is disabled, missing or its query fails, only that stream is empty and the others still appear; the failure is logged and isolated so later streams are unaffected. A malformed caller identity yields a well-formed empty payload with zero counts. _(inb-beh-037; observed)_
- Merge and cap: each source is limited to a bounded number of its newest rows before merging (illustrative; document approvals and alerts newest first). The merged list is sorted newest first, ties by higher severity, then by identifier descending; rows without a timestamp (all change-request rows) sort after dated rows. The merged list is then cut to the requested cap while counts keep the pre-cap values. Approvals count plus alerts count equals total. _(inb-beh-038; observed)_
- Severity rules: every approval row is warning. An alert's severity is derived from its notification type label by case-insensitive keyword matching: labels suggesting lateness, rejection, failure, breach or escalation map to critical; otherwise labels suggesting an upcoming deadline, expiry, pending work, reminder or review map to warning; otherwise info. Critical hints take precedence over warning hints when both are present; a missing label is info. Any unknown or missing severity on a row is treated as info when sorting. The destination may replace the keyword heuristic with its own explicit mapping (see open questions). _(inb-beh-039; observed)_
- Per-user item state: the inbox applies the caller's own recorded states on the way out. Dismissed rows are removed before counting; acknowledged rows stay and are flagged acknowledged; rows without state are flagged not acknowledged; an unrecognised stored state leaves the row unchanged. States are stored per user and per row identifier, never shared; one user's dismissal does not affect another approver of the same step or another recipient. If the state lookup fails, the inbox is built as if nothing had been acted on (fail open) so a pending approval is never hidden by a failed query. _(inb-beh-040; observed)_
- Acting on a row (acknowledge or dismiss): ownership is checked first against the caller's own inbox as it would be built without applying per-user states, so a row already acted on can be acted on again; an identifier not found there answers not-found without recording anything (a write never silently succeeds for foreign or unknown ids, unlike the read path which silently drops). Acting twice on one row overwrites the single stored state (acknowledge then dismiss leaves one dismissed state). Acknowledge changes nothing outside the inbox, including the alert's read flag. Dismissing an alert also marks the caller's own notification read with a read timestamp (the update is limited to the caller's own notification and failure to apply it, for instance when the notification feature is disabled, does not fail the action). Dismissing an approval leaves the step pending in its owning feature. _(inb-beh-041; observed)_
- Restore: looks up the caller's own stored state for that identifier; when none exists it answers not-found; otherwise the state is deleted, the row reappears and the response carries a null state and no findings. Restoring a dismissed alert marks the notification unread again (clearing its read timestamp) so the row is not left invisible. Ownership for restore is established by the existence of the caller's own state, which is why it works even though a dismissed alert has left the unread set. Restoring an acknowledged row only deletes the state. _(inb-beh-042; observed)_
- Action validation: three rules run on (row identifier, requested state). Identifier recognised (blocking): must be well-formed and name a kind of pending work the inbox produces. State known (blocking): must be acknowledged or dismissed. Dismissal decides nothing (informational, non-blocking): when an approval row is dismissed, a finding says the approval was removed from the inbox but is still pending a decision and suggests deciding it in the area where it lives; it is stored with the state and returned in the response; alert dismissals produce no finding. Blocking findings are all reported together. A malformed identifier is rejected with validation findings before any ownership check. Ownership is checked before the state rule, so an unknown state on a foreign row answers not-found. Repeating an action replaces the stored findings. Behavior when the validation capability is unavailable is a decision point (see open questions). _(inb-beh-043; observed)_
- Navigation count badges: a small per-user map of counts used to annotate navigation entries, each computed over the caller's accessible live projects (or one project when requested). Illustrative categories: invoices awaiting approval (warning tone); open information requests; open punch items; quality non-conformance reports not yet closed or voided (warning tone); a combined issues count equal to the sum of the information-request, punch and non-conformance counts that could be computed; the caller's own open tasks; tender packages whose deadline falls within a short upcoming window including today (tone danger when the nearest deadline is today and warning otherwise, plus the number of days until the nearest deadline). Each entry carries a count, a coarse kind classification, a tone (neutral unless stated) and, for tenders only, the days to the nearest deadline. Zero counts are omitted. A badge whose count fails is left out without failing the rest. An empty scope returns an empty map. The response also echoes the requested project id (or null). Exact keys, labels and the full category list are destination decisions. _(inb-beh-044; observed)_
- Tender deadline parsing: deadlines are free text; text that can be read as a calendar date (with or without a time component) yields a calendar day; anything else, or missing, is ignored. Past deadlines and those beyond the window are not counted. Only a bounded number of live tender deadlines is examined per request (illustrative). _(inb-beh-045; observed)_
- Inbox rows are ordered newest first; ties break by higher severity first, then by id descending, so the order is fully deterministic; rows without a timestamp sort last. Re-sorting does not mutate the input. Unknown or missing severity is treated as informational. The server applies the same order before capping. _(inb-beh-024; observed)_
- Inbox triage filters (type all/approval/alert; project all or one; severity all or one) combine with AND. A row with no project never matches a specific-project filter. Project choices are the distinct projects present, labelled by name (falling back to id), sorted by name; severity choices are those present, most severe first; project and severity selectors appear only when more than one choice exists. Segment counts for type reflect the other active filters so each count equals the list obtained by choosing it. A clear-filters action appears when any filter is narrowing. The chosen type and severity may be saved as a per-page default; project is not saved. _(inb-beh-025; observed)_
- Acknowledge keeps the row in the list flagged as seen (visually receded) and changes nothing else; it can be reversed. Dismiss removes the row from the caller's list, also marks an alert read so the notification list agrees, and leaves an approval pending in its owning area (dismissing is triage, not a decision). Restore reverses either. These are per-user states, enforced server-side. _(inb-beh-026; observed)_
- After dismissing, a transient message says the item was removed and offers an undo for a short window (illustratively several seconds); for an approval the message also states the approval is still pending a decision. Undo works even after the row has left the list. Any action refreshes every inbox view (widget and page) so they agree. _(inb-beh-027; observed)_
- Acknowledge, dismiss and restore are idempotent from the client's view: a not-found answer to a repeated action is treated as success with the intended end state and no findings; any other failure is surfaced. The server answer carries the item id, the resulting state (acknowledged, dismissed or none) and optional non-blocking findings. Whether the server itself should answer repeated actions idempotently is a decision point (see open questions). _(inb-beh-028; observed)_
- Inbox row display: title resolved from the title key with the row's parameters, falling back to the supplied title, then to the literal title passed through a generic translation entry, then to a generic action-required label; whitespace-only values count as empty. Relative age is shown with a just-now style label under a minute, then minutes, hours, days; unparseable or missing times show nothing. Rows with a link are clickable; the open control and the action controls are separate (not nested). Approvals carry a badge. _(inb-beh-029; observed)_
- Inbox view states: loading placeholder; error with a retry; empty (nothing pending); and a distinct filters-hide-everything state when the list is non-empty but the filter excludes all rows. Query results are considered fresh for a short period, refetch on window focus, and do not auto-retry. _(inb-beh-030; observed)_
- Notification list screen: filter all/unread/read maps to the read-state query; changing the filter returns to the first page; paged with a fixed page size; paging controls appear only when more than one page exists. Rows are grouped by today, yesterday, previous seven days and earlier (local calendar days). Opening a row marks it read if unread and navigates to its link. Unread rows are emphasised. Title and body fall back from translation, to the server-rendered text, to a humanised form of the key's last segment. Mark-all-read is offered only when unread exist; clear-all deletes every row on the current page; deleting shows a pending state on that row. Every mutation refreshes the list, the unread badge and the bell dropdown. _(inb-beh-031; observed)_
- Preferences screen defaults: with no stored row the in-app cell shows on/realtime and email and webhook cells show off/realtime; changing a switch or cadence saves immediately (upsert) with no global save step; the cadence selector is disabled while the cell is off; failure shows a retryable save error; the screen links to the integrations area because connected chat integrations receive the same notifications filtered by their own event lists. _(inb-beh-032; observed)_

## Inputs

- List notifications: optional read-state filter (true, false or absent), bounded page size (illustrative default fifty, maximum one hundred), offset of 0 or more. _(inb-in-001; observed)_
- Upsert preference: event kind (bounded length), channel (email, in-app, webhook or a no-delivery value), enabled flag (default true), cadence (realtime, hourly or daily; default realtime). One row per user, event kind and channel. _(inb-in-002; observed)_
- Manual digest flush: channel email, in-app or webhook (default email). _(inb-in-003; observed)_
- Webhook target create: name, http(s) address that must pass the external-address policy, event filter (default wildcard), optional secret, active flag; each text input has a bounded length. Update accepts any subset; an empty-string secret clears it. _(inb-in-004; observed)_
- Combined inbox fetch: a bounded row cap with a modest default and no other parameters (the caller is taken from the session, never from input). Acknowledge, dismiss and restore take only the row's stable identifier as a path value; the requested state is fixed by which action is called. Navigation badges take an optional single project id. _(inb-in-005; observed)_
- Push channel: the access credential is supplied in the first client frame; no other client traffic is meaningful besides the text keep-alive. _(inb-in-006; observed)_

## Outputs

- Mark-read answers success or not-found (also when already read); mark-all answers the count changed; unread-count answers a single number; delete answers no-content or not-found; preference upsert answers the stored preference including timestamps; list preferences answers all of the caller's rows. _(inb-out-001; observed)_
- Manual digest flush answers the channel and the number of queued rows sent. Webhook target responses never reveal the secret, only whether one is set, and add the last status, last attempt time, failure count and a machine-readable reason when the address is currently undeliverable (internal address, metadata address, invalid address). _(inb-out-002; observed)_
- Notification payload exposed to chat connectors and live push carries notification id, user id, type, related record, title key, body key, parameters and link. _(inb-out-003; observed)_

## States and transitions

- Notification: unread to read (stamped with read time) via open, mark-read or mark-all; read rows are never flipped back by those actions; removal by owner delete or retention cleanup. _(inb-st-001; observed)_
- Digest item: queued (with scheduled time) to sent (stamped) exactly once. _(inb-st-002; observed)_
- Inbox row per user: listed, acknowledged (still listed, flagged), dismissed (not returned), back to listed on restore. _(inb-st-003; observed)_
- Per-user row state machine: none to acknowledged (acknowledge), none or acknowledged to dismissed (dismiss, replaces), acknowledged or dismissed to none (restore). Dismissing an alert additionally moves the caller's notification from unread to read; restoring a dismissed alert moves it back to unread. A notification that was marked read by other means while acknowledged simply leaves the unread set and so leaves the inbox. _(inb-st-005; observed)_
- Webhook target: active with failure count zero, rising failure count, skipped at the lower threshold, deactivated at the higher threshold, back to active only by operator re-save or reset. _(inb-st-004; observed)_

## Timing and ordering

- Illustrative cadences: digest flush every few minutes per channel; cleanup on a daily cycle; retry backoff starting in the tens of seconds, doubling, capped at the task interval; webhook request timeout of a few seconds; undo window of several seconds; short freshness windows (tens of seconds) for inbox and notification queries. The destination chooses its own values. _(inb-time-001; observed)_
- Notification handlers run after the originating request commits (detached publishing), each in a fresh transaction. Realtime email is released after the in-app write commits. _(inb-time-002; observed)_
- Notification list ordering is newest first; inbox ordering is newest first with severity then id tie-breaks; preferences list order is unspecified. _(inb-time-003; observed)_

## Edge cases

- The reader's language lookup failing does not fail the list; English is used. _(inb-edge-001; observed)_
- Digest cadence queueing schedules the item one hour (hourly) or twenty-four hours (daily) after queueing time, as a flat offset rather than a fixed local time of day. _(inb-edge-002; observed)_
- A digest flush with nothing due returns zero without side effects; if another flush claimed all rows first it also returns zero. _(inb-edge-003; observed)_
- Self-notification suppression: an approval whose first approver equals the submitter, an information request assigned by the assignee themselves, and an answer written by the requester produce no notification. A reassignment that carries no actor always notifies. _(inb-edge-004; observed)_
- One meeting action item without an owner is skipped while others in the same meeting still notify; items without a task id notify without a link. _(inb-edge-005; observed)_
- Connected chat integrations are told about each stored notification independently of the preferences matrix; the matrix controls only the three listed channels. _(inb-edge-007; inferred)_

## Errors

- Marking read a notification that is missing, already read or not owned answers not-found; deleting one that is missing or not owned answers not-found (ownership is never distinguished from absence). _(inb-err-001; observed)_
- Webhook administration and manual digest flush answer forbidden unless the caller is an administrator or holds a dedicated notification-administration permission; create/update/delete additionally require a stricter administrative permission. Updating or deleting an unknown target answers not-found. Create/update with an internal, loopback, private or metadata address is rejected at validation. _(inb-err-002; observed)_
- Push channel closes with policy-violation (code 1008) when the token is missing, invalid, expired, of the wrong kind, names a missing or inactive user, or has a non-id subject; it closes with internal-error (code 1011) when authentication could not be judged (infrastructure fault). The two are deliberately distinguished because clients do not reconnect on this channel. _(inb-err-003; observed)_
- Out-of-range paging or cap values and invalid preference channel/cadence values are rejected as validation errors. _(inb-err-004; observed)_
- Email send failures and crashes are logged and never propagate; webhook batch failures never propagate. _(inb-err-005; observed)_
- Inbox action errors: an id that is well-formed and of a recognised kind but absent from the caller's own inbox (including another user's alert) answers not-found with a generic message; restore with no stored state answers not-found; a malformed or unrecognised-kind id, or a blocking rule failure, answers an unprocessable-input error whose body names a message and the list of findings (rule identifier, severity, message, suggestion); an out-of-range row cap on the list is a validation error. The inbox list itself never answers forbidden and answers success with empty data when nothing is pending. _(inb-err-006; observed)_
- Navigation badges: a requested project the caller cannot open, or one that does not exist, answers not-found; an unscoped request for a caller with no accessible live project returns success with no badges. _(inb-err-007; observed)_

## What it must not do

- No user can read, mark, delete or receive push for another user's notifications. _(inb-neg-001; observed)_
- Notification handlers never break or roll back the originating action, and a disabled preference never causes an in-app, email or webhook send for that user/event/channel. _(inb-neg-002; observed)_
- Dismissing an approval never decides or removes it in its owning area. _(inb-neg-003; observed)_
- The webhook-target secret is never returned to any client. _(inb-neg-004; observed)_
- The combined inbox never consults notification preferences; it reads whatever unread in-app notifications exist. A suppressed or queued in-app event therefore never appears as an alert (indirect effect only), and handlers that store in-app notifications unconditionally always do. The digest channel preference does not apply to direct in-app creation by simple handlers that bypass preference routing. _(inb-neg-005; observed)_

## Security

- All user-facing notification operations act only on the caller's own rows. The combined inbox read is scoped to projects the caller can access, with absence and denial indistinguishable (rows are dropped, never refused). Writes are stricter: acting on an id not in the caller's own inbox answers not-found, so ids cannot be probed through writes. Per-user item states are readable and writable only by their owner. Navigation badges for a project the caller cannot open answer not-found exactly like a missing project. _(inb-sec-001; observed)_
- Outbound webhooks are an exfiltration risk, so management is administrator-only, addresses are restricted to external hosts (checked again after name resolution at every delivery), bodies can be signed, and each delivery has a unique idempotency identifier. _(inb-sec-002; observed)_
- Push authentication re-checks the user against the database so a forged token for an unknown user cannot open a channel. _(inb-sec-003; observed)_
- Email subjects and bodies expose only a project name and record references, and click-through links in the in-app rows stay relative; only email resolves them to absolute addresses. Client code is expected to apply a shared link-safety check before navigating. _(inb-sec-004; inferred)_

## Invariants

- Unread count equals the number of the caller's rows with the read flag false, independent of paging or filter. _(inb-inv-001; observed)_
- For one user, event kind and channel there is at most one preference. _(inb-inv-002; observed)_
- A digest item is sent at most once, and the count returned equals queued items sent. _(inb-inv-003; observed)_
- Inbox sort is a total order; inbox counts are pre-cap, post-scope and post-dismissal on the server (approvals count plus alerts count equals total) and the client keeps them on server totals. _(inb-inv-004; observed)_
- A recipient list never contains the actor, duplicates or non-user values. _(inb-inv-005; observed)_

## Notes

- Stored text keys and parameters are the durable contract; clients resolve them through their own translation tables and use server-rendered fallbacks only when the key is missing. Destination must keep stored rows renderable after translations change. _(inb-compat-001; derived)_
- Webhook consumers depend on the envelope fields, the signature scheme (keyed SHA-256 of the exact body), the event-kind header and the idempotency header. Whether any exact header spellings or signature formatting must be preserved is a destination decision. _(inb-compat-002; inferred)_
- Event kinds use dotted namespaces and are matched by exact or prefix patterns; preferences and webhook filters reference these kinds, so destination event kinds must remain stable or be migrated. _(inb-compat-003; derived)_
- Numeric limits, thresholds, intervals, row caps and window sizes in this spec are illustrative orders of magnitude. The destination chooses its own values and need not match any stated number. Row identifier formats and navigation badge keys or labels are likewise destination choices unless a client integration requires otherwise. _(inb-compat-004; derived)_

## Non-goals

- No source code, identifiers, comments or message strings are reproduced.
- Do not reproduce origin provenance markers.
- Exact visual styling, icons, colours and layout of inbox and notification screens are not specified.
- Internal chat-connector delivery, e-mail transport configuration and the mail budget policy are out of scope for this unit.
- Internal storage layout of the per-user item states is not specified; only the observable one-state-per-user-and-row semantics are.
- The destination is not required to mirror the origin's module structure, naming or event vocabulary.

## Open questions (decisions for QC Manager)

- Should the destination list every pending step assigned to the caller (as observed) or only the step whose turn it is in a multi-step chain? Observed behavior does not check turn order.
- Each source is bounded to a number of newest rows before merging, so counts can saturate at that bound; should the destination report true totals instead?
- Observed ordering compares timestamps as text, so mixed formats (offsets or precision) could misorder rows; should the destination compare real instants? Rows of one approval kind carry no timestamp and always sort after dated rows, so old alerts can outrank newer approvals; is that intended?
- A repeated dismiss of an alert answers not-found while a repeated dismiss of an approval succeeds; should the destination make all repeated actions idempotent on the server?
- Ownership checks for acting on a row are performed by scanning a bounded set of the caller's inbox rows, so rows beyond that bound would answer not-found; should the destination look up ownership directly instead?
- When the validation capability is unavailable or resolves to no rules, the action proceeds unvalidated and returns no findings (malformed identifiers are still rejected); should the destination keep this or require validation?
- Should row identifier formats, navigation badge keys and badge kind labels be kept for client compatibility, or may the destination define its own?
- Alert severity is a keyword heuristic over notification type labels, and some hint words overlap; keep as observed, or replace with an explicit per-kind mapping?
- For administrators, alerts naming projects outside the accessible list are still shown while approvals stay limited to the list; confirm that asymmetry is wanted. Also decide whether an optional organisation-level scope narrowing applies to administrators.
- How often should navigation badges refresh? The client refresh cadence was not observed.
- What is the mail-budget policy (per-recipient daily limit, behaviour on rejection, treatment of system or placeholder accounts)? Only its call site was observed.
- Recipient rules and message content for the less-analysed generator groups were inventoried only coarsely; which of them does the destination need?
- Should destination preserve exact webhook header spellings and the dotted event-kind vocabulary or define its own?
- Should the daily digest time be a flat 24-hour offset or a fixed local time of day?
- Do the shared helpers for safe link navigation and translation fallback behave as inferred?
- Are in-app digest items meant to bypass later preference changes?
- Should the destination accept the access credential only in the first frame of the push channel, or also support a transitional alternative?
- Should the event-kind catalogue include entries that nothing currently emits, to keep stored preferences valid?
- Should record-creation acknowledgements to creators, and deletion echoes that lack an actor, exist in the destination?
- Does the destination need aliasing for older stored notification key conventions?
